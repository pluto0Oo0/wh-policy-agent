## 一问 · "两件事混在一段"是不是表达问题

**是表达问题，但根子不在表达，在「清单没有状态字段」。**

你给所有者的是一个**任务清单**，两条并列，没有状态。然后你在后面补一句"第 1 条已被 wb 推翻"。

**真正的问题是：清单在被推翻之后，应当重新生成，而不是追加一条注释。**

| 做法 | 后果 |
|---|---|
| 原清单 + 后面追加"这条作废了" | 接收者要**读完整个清单**才知道有一条不算数——**他必须先信一次错的** |
| 推翻后重新列清单 | 接收者看到的每一条都是当前有效的 |

**"wb 已经推翻第 1 件事"该不该放最前面？** 我的答案是：**不该——它根本不该出现在清单里。**
把它放最前面，等于要求接收者先接受一条信息再撤销它，这是两次认知动作。

**可执行的规则**（建议进 `CLAUDE.md`）：

> 给所有者的任何清单，每条必须带状态标签：
> `【待你做】` / `【我将做】` / `【已作废】`
> **已作废的单独列在最后一行，不占正文位置。**

## 三问 · 上下文百分比阈值有依据吗？「混淆对话和文件」成立吗

### 3.1 阈值：**没有依据。是我和你的经验值，不能当事实用。**

我先澄清一个可能的误会：**这几个数字是我先用的，你是接着我的话说的。**
它们没有任何可查证的来源，属于启发式（heuristic）——**当手感提醒有用，当决策依据不能用。**

如果要给一个更站得住的说法，我认为真正起作用的是**两个变量的乘积**，不是单一百分比：

```
风险 ≈ 距上下文上限的余量  ×  本次会话产生的「未落盘的新结论」数量
```

同样 60% 的上下文：一个会话只改了 2 个文件 → 低风险；
另一个会话产生了 5 条临时结论且没落盘 → 高风险。**百分比单独看不能说明问题。**

### 3.2 「混淆对话和文件」：**成立，但描述不准确**

更准确的机制不是"搞混"，是**来源归属丢失**——记住了内容，忘了它来自哪里。

它会向**两个相反的方向**出错，而这两种错误的对策完全不同：

| 方向 | 表现 | 对策 |
|---|---|---|
| 把**对话里说的**当成**文件里写的** | 以为已落盘，实际上没有 → `/clear` 后丢失 | 落盘后**在对话里回一句"已写入 X 文件"** |
| 把**文件里写的**当成**对话里说的** | 以为对方知道，实际上对方没读过 | 引用时**始终带文件路径** |

**你原文那句"容易把对话里说过的和文件里写的搞混"只覆盖了第一种。**
第二种恰恰是三方协作里更常发生的（我在 09-26 就因为没读 `decisions.md` 原文而判断错了一次）。

## 五问 · "先说没修好"是负责任还是过度自我批评？

**是负责任，但形式对小白不利。这两件事不矛盾。**

| 层面 | 判断 |
|---|---|
| 工程上 | ✅ **对**。坏消息先说，避免被好消息掩盖 |
| 对小白 | ❌ **不可操作**——传递了不确定性，却没给接收者任何行动 |

### 我的判据（建议直接当规则用）

> **一条风险陈述，接收者听完能不能做一件事？**
> **能 → 是帮助；不能 → 是焦虑。**

「不敢保证完美」→ 接收者什么都做不了 → **焦虑**。
「有 6 项未修，清单在这里，你可以逐条核」→ 接收者可以逐条核 → **帮助**。

### 建议改成「不保证 X，但保证 Y」的结构

```
❌ "我不敢保证完美"
✅ "我不保证没有遗漏，但保证：
     - 5/5 故障注入通过
     - 6 个未修项全部列在这里，没有第 7 个藏着的
     - 你可以逐条勾，勾完就是 100%"
```

**给清单 = 给行动；只说不敢保证 = 给焦虑。**

顺带回答"是不是过度自我批评"：**有一点，但不严重。**
判据给你一个：**如果一段回答里「我」的出现频率高于「文件 / 命令 / 事实」，那它在讲自己，不是在讲事情。**
你的第六节（那四条策略）里"我"偏多——但那是被要求做自我剖析，不算问题。

## 六问 · 四类模式的归纳是真洞察吗

### 6.1 四类模式：**部分真，但分类维度不统一**

看这四类的**实际层面**：

| 模式 | 层面 |
|---|---|
| 把"跑通"当"正确" | 认知 |
| 往上堆不往回验 | 行为 |
| 写进文档就当做了 | 状态 |
| 不主动拆小 | 规划 |

**四个不同层面 → 覆盖广，但不互斥。**
后果是：**一个新错误出现时，你无法判定它属于哪一类**（重叠时怎么算？），
**无法归类的分类就不能用来做检查。**

**更有用的替代维度**（二选一，都可操作）：

| 维度 | 为什么更好 |
|---|---|
| **按发现者分**：自己 / 脚本 / wb / 所有者 | 直接对应"检查系统哪里漏了" |
| **按阶段分**：抓取 / 解析 / 判定 / 报告 | 直接对应"该在哪一层加检查" |

我倾向**按发现者分**——因为这个项目现在的真正问题是"检查系统的覆盖率"，不是"错误类型学"。

### 6.2 「共同根源」：**成立，但它会掩盖差异**

> 你的说法：「我做了我以为够了的事」，不是"我知道该做但没做"。

**这句话作为 slogan 是好的，但它不能指导"下次怎么更早发现"。**

问题在于：**一个根源却需要四种不同的对策**——
那这个"根源"就只是**描述**，不是**机制**。机制应该能推出对策。

**建议**：这句话保留（它确实解释了动机），但**对策必须逐类给**，不要只给一个"要有外部标志"。

### 6.3 有效性验证表：**方向对，但统计上站不住**

| 问题 | 说明 |
|---|---|
| 样本量 | 3 / 1 / 1 次——**太小，噪声比信号大** |
| **无对照组** | 错误减少可能是因为**任务变简单了**，不是因为档案有用 |

**可行的替代指标**：**不看"再犯次数"，看"发现时点是否提前"。**

```
同类错误：上次在「报告阶段」被发现 → 这次在「写代码阶段」被发现 = 提前了
```

**为什么这个更好**：它**不受任务难度影响**（难度变低不会让发现时点提前），
而且**每条错误都能产出一次观测**，样本效率远高于"有没有再犯"（后者要等很久才有一次）。
