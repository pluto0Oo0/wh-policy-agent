### B 组 · 注入故障：把 URL 里的文章 ID 改一位

## 二、为什么你的质疑方向对、结论错

你的推理是：
> 两者可能由同一 CMS 字段渲染 → 不是独立信源 → 交叉验证恒真 → 等于没验证

**错在最后一步。** 关键在于：**这个检查验证的目标是什么？**

| 如果目标是 | 恒真意味着 |
|---|---|
| 证明「标题这个字符串是对的」 | ❌ 无效（你说得对）|
| **证明「列表页这条记录 ↔ 它指向的详情页」对应正确** | ✅ **正常，而且不一致就是真错误** |

**方案 A 验的是后者。**

它排掉的是本项目**真实踩过**的那些坑：
- URL 拼错（那个 `index_1.shtml` 少下划线的坑）
- 抓到跳转页 / 站点首页
- 列表项与详情页错位

这些**恰恰是最危险的一类**——程序全绿、数据齐全、只是指错了地方。

### 一般化的判断标准（建议写进 CLAUDE.md）

> **判断一个检查是否有效，看它能不能抓到「注入的故障」，
> 而不是看它正常运行时会不会全部通过。**
>
> 一个永远不会报警的检查，和没有这个检查，是同一件事。

**这条可以直接解决你担心的「检查器假通过」**——`verify_title_format.py` 空输入落 `else` 输出 ✅，
那个 bug 用故障注入一次就能抓出来：**喂空输入，看它是不是还输出 ✅。**

## 三、额外收获：一个比现有更硬的软 404 判据

B 组实验暴露了一个规律：

```
正常页面：<title>政策标题 - 武汉市人民政府门户网站</title>
页面不存在：<title>武汉市人民政府门户网站</title>     ← 没有前半段，也没有 " - "
```

**→ 判据：详情页 `<title>` 去掉站点后缀后为空 ⇒ 页面不存在。**

这比现有的 `len(html) < 1000` 硬得多：
- 长度检查靠猜阈值，改版后可能失效
- **这个是布尔判断，且来自 CMS 的实际行为**

**建议**：`crawl_detail` 里用这个做软 404 检测，**和长度检查并存**（长度检查兜底，title 判断精确）。

## 四、纠正一个优先级：你担心错地方了

你的通报把重点放在「skill 不会自动触发 → 靠自觉 → 这是唯一没解决的环节」。

**我认为真正的顺序反了：**

| 你担心的 | 我认为更先的 |
|---|---|
| 检查触发不了（机制问题） | **检查本身可能是恒真的（有效性问题）** |

**理由很简单**：如果一个检查恒真，那就算每次都触发，它也不会拦住任何东西。
**先证明检查有效，再解决怎么触发它——否则加了 hook 也只是多打印几行没用的字。**

**具体建议**：
1. 不要急着上 `PreToolUse` 硬拦 —— **这点我同意你的判断**（误伤风险、配置复杂、出错难排查）
2. `Stop` hook 提醒够用，但**「观察两周」不是验证有效性的方法，是等结果**
3. **更快的方法**：给 `deliver-check` 加一个自检模式，改完检查器就跑一次故障注入

```bash
# 建议：每次改检查器后跑
python scripts/check_deliver.py --selftest
```

**它做什么**：构造已知的坏输入（空文件 / 缺字段 / URL 错位 / 超长文件），
**断言检查器必须报错**。哪个没报错，哪个就是恒真的检查。

**这是把「检查器自己的 bug 比不报警更危险」落到可执行的一步。**
