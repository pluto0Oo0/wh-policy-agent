# 项目全流程总结

> **用途**：记录这个项目**至今为止确定下来的工作流程**，包括三方协作方式。
> **给谁看**：所有者（了解全貌）+ wb（了解它在流程里的位置）+ 下一个会话的 CC（恢复上下文）。
> **什么时候更新**：流程有变化时。

---

## 一、这个项目是什么

**武汉大学生政策条件判定助手。**

输入一个人的情况 → 输出「能享受哪些政策 + 省多少钱 + 依据哪一条 + 还缺什么」。

**目标不是"做个 AI 问答"，是"做判定"**——判定是对错确定的，能自动评测。

---

## 二、三方协作结构

```
        所有者（你）
       /            \
      ↓              ↓
    CC（执行）      wb（审查）
      ↓              ↓
   写代码跑验证    提建议查盲区
      \            /
       →  _handoff/ 交接区  ←
```

| 角色 | 职责 | 边界 |
|---|---|---|
| **所有者** | 定方向、审码、决策、学习 | 唯一有决策权的人 |
| **CC** | 写代码、跑验证、执行 | **不能自己决定方向**；必须逐行讲解代码 |
| **wb** | 审查、建议、查盲区 | **不能直接执行**；只能写 `inbox/` |
| **脚本/hook** | 自动跑检查 | 只能查可枚举的问题 |

### 关键设计：三道过滤

**审查意见要经过三道路径才能变成代码：**

```
wb 写建议 → inbox/
    ↓ ① 过滤：CC 不得直接执行，必须先报告
所有者看 → 决定采纳哪些
    ↓ ② 过滤：CC 核实（可能反驳）
CC 执行 → 改代码/文档
    ↓ ③ 过滤：跑 check_deliver + reflect 验证
交付
```

**为什么需要三道**：

| 过滤层 | 防什么 |
|---|---|
| ① | **防"文件夹绕过人工过滤"**——对话里贴的意见天然有人过一遍；文件直接躺目录里没有 |
| ② | **防误信**——wb 也可能错（它自己认过 3 次错） |
| ③ | **防"改完了但其实没改对"** |

## 三、完整工作流（从想法到交付）

### 阶段 A · 立项

| 步 | 做什么 | 产出 |
|---|---|---|
| 1 | 明确目标（要解决的**具体**问题，不是技术演示） | 一句话产品定义 |
| 2 | 验证数据源可行性 | **能不能拿到数据、内容对不对** |
| 3 | 写 SPEC | `docs/SPEC.md`（唯一编码依据） |
| 4 | 写 PLAN | `docs/PLAN.md`（时间线） |
| 5 | 写 CLAUDE.md | 项目约定（硬性规则） |

### 阶段 B · 每个模块的开发循环

```
① CC 写代码（单次会话 ≤200 行）
    ↓
② 跑自检脚本 check_deliver.py —— exit code 必须为 0
    ↓
③ 跑 /reflect 审自己的判断
    ↓
④ **逐行讲给所有者听** ← 这一步最常被跳过，但最重要
    ↓
⑤ 所有者确认 → commit
    ↓
⑥ 阶段性交付时 → 交 wb 审查
```

**⚠️ 第 ④ 步的由来**：项目的**第一目标不是交付，是能力**。
所有者是"能交付但读不懂代码"的状态——**代码写完了但没讲，等于白写。**

### 阶段 C · 与 wb 的交接循环

```
wb 写 inbox/xxx.md
    ↓
CC 开工时 hook 自动提醒（SessionStart）
    ↓
CC 报告给所有者（列出标题，不执行）
    ↓
所有者决定 → CC 核实 → 有分歧就查
    ↓
CC 写 outbox/ 回复
    ↓
处理完移 done/
```

**交接文件的固定格式**（`_handoff/README.md` 有完整版）：

**开头四行**：来源 / 优先级 / 性质（建议不是命令）/ 一句话结论
**结尾三段**：
1. **请你查证**（我没验证过的）
2. **我已验证，可直接采信**（防重复劳动）
3. **不同意就说**（邀请反驳）

**第 3 段不是客套**——**双向纠正目前成功 5 次**（wb→CC 3 次、CC→wb 2 次）。

## 四、审查系统（四层 + 两个 hook）

| 层 | 工具 | 检查什么 | 触发方式 |
|---|---|---|---|
| 1 | `check_deliver.py` | 数据格式 / 行数 / 静默吞错 / 假对比 | **skill 自动注入结果** |
| 2 | `/code-review` | 代码质量 | 手动 |
| 3 | `/reflect` | **我自己的判断** | 手动（hook 提醒） |
| 4 | wb | **我没想到的角度** | 阶段交付 |

**两个 hook**：
- `SessionStart` → 开工打印 inbox 状态 + 高发错误 + 心跳
- `Stop` → 每轮打印"宣布完成前必答六问" + skill 调用提醒

**四层不重叠，是互补的**：

| 谁审 | 强项 | 盲区 |
|---|---|---|
| 我自己 | 知道全部上下文 | **审不出"我没想到的"** |
| 脚本 | 不会被忽悠 | 只能查**可枚举**的 |
| /reflect | 强制"敌对视角" | 还是我的知识范围 |
| wb | **完全独立视角** | 看不到代码细节 |

## 八、这个流程为什么是这样设计的

**核心逻辑**：**所有者是"能交付但读不懂代码"的状态。**

所以整个流程的设计原则是：

> **凡是可以外部化的检查，都不靠人记。**

| 靠什么 | 例子 |
|---|---|
| ❌ 靠记忆 | "记得跑自检" → **失败过 3 次** |
| ✅ 靠 hook | 开工自动打印 inbox |
| ✅ 靠脚本 | `check_deliver.py` 的 exit code |
| ✅ 靠 skill 注入 | `!` 语法把检查结果**怼到眼前** |
| ✅ 靠格式 | 交接文件三段式固定 |

**一句话**：
> **原则靠记忆触发，动作靠时机触发。**
> **写成"动作"的规则会被执行，写成"原则"的会被忘记。**

**实证**：`CLAUDE.md` 第 10 条（"要自检"）是原则，写完当天违反两次；
第 10.1 条（"六问"）是动作，配合 hook，开始起作用。
