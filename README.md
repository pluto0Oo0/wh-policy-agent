# wh-policy-agent

> **武汉大学生政策条件判定助手** —— 输入一份个人画像，输出「能享受哪些政策 + 省多少钱 + 依据政策原文哪一条 + 还缺什么」。

**不是问答机器人，是判定器。** 检索只是前置步骤，产品是判定。

---

## 这个项目解决什么问题

武汉面向大学生的政策散落在市人社局、市住房和城市更新局、各区政府官网等十几个渠道。同一类政策在不同区口径不同，已废止的页面从不标注失效。毕业生往往不知道自己适用哪一条、卡在哪一条、能省多少。

传统做法是去窗口问。问题在于：口径因人而异，且新人问不完。

本系统输入一份个人画像，输出**可解释的判定结果**：

| 输出 | 说明 |
|---|---|
| ✅ / ❌ / ❓ | 符合 / 不符合 / **信息不足**（第三态独立，不并入「不符合」） |
| 逐条依据 | 每条结论挂政策名 + 文号 + **原文摘录** |
| 金额 | 满足条件的计算类条款给出具体减免额 |
| 缺项清单 | 信息不足时主动追问，而不是硬给答案 |
| 办理指引 | 原文照抄受理部门与联系方式 |

## 快速开始

```bash
# 1. 建虚拟环境（项目自带 requirements.txt）
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt

# 2. 跑判定（默认取第一条政策）
.venv/Scripts/python.exe -m src.cli ask --profile data/profile.json

# 3. 指定政策
.venv/Scripts/python.exe -m src.cli ask --profile data/profile.json --policy t20220608_1983869

# 4. 跑评测（输出三类准确率 + 混淆矩阵）
.venv/Scripts/python.exe scripts/evaluate.py

# 5. 自检（故障注入：验证检查器不是恒真的）
.venv/Scripts/python.exe scripts/selftest.py
```

## 技术要点（每条都有「为什么」）

完整推导见 `notes/decisions.md`（每条含「结论 + 为什么不选另一个 + 代价是什么」）。

### 1. 判定用纯代码，不用 LLM

比大小、区间判断、金额封顶是**确定性问题**。交给模型只会引入不确定性和幻觉，且无法保证每条结论可溯源到具体条款。模型化能力如后续引入，只用于辅助从文本抽取候选条件，**不参与最终资格结论**。

### 2. 人群分层：`2022-06-07` 是政策分界，不是「取最新版本」

武汉安居政策存在**合法的双轨**：

- 2022-06-07 前留汉的 → 按《武房规〔2018〕2 号》
- 2022-06-07 后留汉的 → 按《武政办〔2022〕78 号》

两套规则在毕业年限、户籍、社保要求上均不相同。**「取最新版本」会让一整类人群得到错误答案**，所以必须先判定适用轨道，再取对应规则。这就是 `applies_to_cohort` 字段的用途。

### 3. 三态判定：信息不足必须独立成态

「用户没填社保时间」和「用户确实不符合条件」是两种性质不同的处境。前者应触发追问，后者才给否定结论。这一区分贯穿条件数据模型、判定引擎、结果展示三个层次。

### 4. 条件结构化：字段—运算符—阈值—条件类型—原文依据

政策条款统一建模为这个五元组，每条**必带原文摘录**，保证结论可溯源。豁免规则（`exempt_when`）独立建模，记录豁免前后的判定结果，避免不同政策中的例外条件相互混用。

### 5. 不建向量库

语料量太小（几十条政策），`BM25 + 元数据过滤` 足够。引入向量库是解决不存在的问题。

## 我的系统什么时候会错

**这一节是给面试官看的，也是这个项目最有用的部分。** 一个说「我的系统不会错」的系统，没人信。

### 已定位、尚未修复的 2 个已知缺陷

| # | 缺陷 | 影响 | 状态 |
|---|---|---|---|
| 1 | **分界日 off-by-one** | `2022-06-07` 前后的判定差一天。轨道会翻转，但两套规则的结论在现有样例里恰好相同，所以评测集抓不到 | 待修 |
| 2 | **`age<45` 被实现成 `age<=45`** | 45 岁边界判错。现有 45 岁样例恰好都是硕博（被豁免），所以评测集同样抓不到 | 待修 |

> **这两个 bug 是怎么发现的**：不是评测集抓到的，是**故障注入**（故意注入已知缺陷，看检查器能不能报警）抓到的。
> 详情见 `scripts/selftest.py` 的设计。
>
> **为什么评测集抓不到，是这个项目最有价值的一课**：
> **评测集只能证明「我测过的输入是对的」，不能证明「我没测过的输入是对的」。**
> 覆盖 52 条规则、50 条样例，依然可能有两个 bug 一个都碰不到。

### 真实踩过的坑（数据层）

| 坑 | 症状 | 后果 |
|---|---|---|
| **数据源停更** | 第一版选的源最新内容停在 2023 年 | 系统会对 2026 年毕业生给出 2023 年的答案 |
| **翻页地址错一个下划线** | `index1.shtml`（漏下划线）返回 HTTP 200、18 万字符，**但 0 条数据** | 程序不报错，只是默默少抓一半 |
| **列表页数据藏在 JS 里** | 286 个 `<a>` 标签里只有 4 个是真政策链接 | 用普通方法抓会得到「这页没数据」的错误结论 |
| **失效页伪装成正常页** | 失效页 `<title>` 退化成纯站点名，**内容长度反而更长**（189,913 vs 116,671 字符） | 所有「按长度判断是否失效」的判据全错 |

这四个坑的共同点：**程序都不报错**。所以本项目的自检规则是硬性的——

> **抓取 0 条、条数低于阈值、内容长度异常 → 直接报错，不静默返回空。**

## 工程纪律

这个项目自带一套「防止自己骗自己」的机制，因为**最容易犯的错误是「程序不报错但结果是垃圾」**。

| 机制 | 作用 |
|---|---|
| **故障注入自检**（`scripts/selftest.py`） | 构造已知坏输入，断言每个检查器**必须报警**。一个永远不会报警的检查，等于没有检查 |
| **交付前检查**（`scripts/check_deliver.py`） | 行数、编码、硬指标、重复项 |
| **每条规则带原文摘录** | 结构断言只能证明「分区对、引文对」，证明不了「语义对」——语义必须人审 |
| **口径分离报告** | 「单文件超 200 行」是软预警，「单次会话新增超 200 行」是硬红线。混算口径会让人无从判断 |

**当前自检状态**：`selftest.py` 6/6 通过，`check_deliver.py` 0 失败。

## 调研结论：为什么这类项目少

前期检索了 **15 个**与政策类相关的公开仓库（就业政策助手、政策问答 App、政策图谱检索、基于 YAML DSL 的资格判定系统等），发现：

- 这些项目**普遍把重心放在检索与问答**，输出形式以自然语言段落为主，**较少给出结构化的逐条判定结论**
- **15 个项目无一给出准确率或召回率等可量化评测数字**，尽管其中部分已具备单元测试或规则覆盖率审计脚本

也就是说，**政策类系统的「判定正确性」至今仍是公开研究中普遍缺失的一环**。本项目的切入点就在这里：**用人工标注的规则基准集 + 可回归的自动化评测**，给这个领域补上一个能验证的数字。
