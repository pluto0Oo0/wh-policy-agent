## 1. 目标函数：先定义「最优」再谈选择

调度人的 18 周目标拆成可考核的形式，春招 AI 应用开发岗需要四样东西：

1. **一个能讲 20 分钟的主力项目**：有真实数据、有工程难点、有评测、有迭代记录。
2. **一个可演示的第二触点**：证明不是只会做一个东西。
3. **AI 辅助开发工作流的熟练度**：wb×CC 协作本身就是面试素材（这点常被忽略）。
4. **简历在春招开闸前定型**：2027 届春招实习通常 2027 年 2–4 月开闸，从现在算起第 14–16 周简历就要冻结。**实际工期比 18 周短 2–4 周。**

推论：任何新方向的边际价值 = 对上面四项的贡献 ÷ 挤占 wh-policy-agent 的小时数。wh-policy-agent 已是「重头」，地位不可动摇——这不是偏好，是算术：主力项目做深 1 厘米，胜过新项目铺开 1 公里。

## 2. 逐候选判定

### A. 直接用官方 skill，不开发 —— 降级为习惯，保留

- 对求职四样贡献为零，作为「项目方向」出局。
- 但有一个免费价值：**自己当用户是 B 最便宜的用户调研**。每周 30 分钟用官方 skill 查自己真实处境的问题，亲身体验「无个性化」到底卡在哪——这比任何需求分析文档都硬。
- 判定：不计入项目时间，不留工程产出。

### B. 个性化 agent —— 真产品空位，但必须压成 MVP 且第 8 周才准启动

**空位属实**：官方 skill = 检索+排序，无个性化（CC 10-19 核实仍成立）；生态里阅读站/App/小程序/MCP/API/数据集全是「分发层」，没人做「知道你是谁」的那层。690 条循证建议 + 日同步结构化数据集 = 内容管道免费送，差异化全在画像模型和行动闭环。

**关键洞察——B 与 wh-policy-agent 同构**：

| 层 | wh-policy-agent | B（个性化 agent） |
|---|---|---|
| 输入 | 用户画像（在读/经济/户籍） | 用户处境（经济/在读/求职中） |
| 引擎 | Python 规则引擎 → 判定可享受政策 | 规则/排序引擎 → 筛出本周 3 件 |
| 输出 | 政策清单 + 省多少钱 | 行动清单 + 预期收益 |
| 闭环 | （弱） | 打卡/复盘/提醒 |

同构的意义：**第二个项目的边际成本远低于第一个**。引擎模式、画像 schema 设计、解释输出的写法、评测方法、wb×CC 工作流——全部复用。面试叙事也从「我做了两个不相关的项目」升级为「我抽象了画像驱动的决策助手模式，落地两个领域」——前者是罗列，后者是架构能力，差一个档次。

**风险控制（硬约束）**：
- B 必须是 MVP：画像表单 → 每周 3 条行动 → 打卡复盘。砍掉 App/小程序形态，先单页 Web 或 CLI。
- **第 8 周设闸门**：wh-policy-agent 达到「可演示 + 真实数据 + 评测跑通」才启动 B；不达标则 B 砍成「官方 skill + 一层个性化 prompt」的 1 周玩具，或直接放弃。闸门存在的理由：B 失败的最大成本不是 B 本身，是拖垮主力项目。

### C. 检索层 —— 维持划掉，补一刀

题目已划掉，同意。补充一个该划掉的深层理由：检索层是「做给别人用」的基础设施，而调度人没有分发渠道；生态里 API（why520-like/htlb-api）、日同步数据集（sin0317/htlb-dataset）、MCP（Helioswei/HowToLiveBetter-Kit）三个坑位都已被占，后入场无差异。

### D. 拆上游仓库当学习样板 —— 放第一周，是倍乘器不是简历条目

- 上游一个月 61.7k star 的 Claude Code 工作流 + 95KB CLAUDE.md + 自检脚本，恰好是调度人刚定稿的协作规范 v2 的**对照组**：人家怎么写约束、怎么做自检、怎么防 AI 跑偏，逐条对照能直接改进 wh-policy-agent 剩余 18 周的执行质量。
- 成本上限 1 周。产出形态：「可搬运模式清单」，每条过自家三测试（主体/抽参/机制），过不了的只当见识不当规则。
- 注意排序逻辑：D 必须放最前，因为它的收益作用于后面所有周；放最后就只剩收藏价值。

## 4. 最不确定的一点（题目要求 2）

**B 的「行动闭环」是否真有用户需求，我没有证据。** 「690 条建议需要个性化分发」是从产品逻辑推出来的，不是从用户行为验证的——打卡/复盘/提醒类产品历史上留存率普遍很差，「书上 7 条 vs 这周 3 件」的差异对真实用户是否构成价值，未知。

但要说明这个不确定的**影响范围有限**：对求职目标，面试官看的是工程决策和判断过程，不是 DAU。它真正威胁的是「B 做不成 MVP 时的时间沉没」——这正是 W8 闸门存在的原因。若未来想把 B 当真产品做，这个不确定升级为 P0，需要先花 1 周做需求验证再动工。

## 5. 这道题本身的问题（题目要求 3，直说）

1. **四个候选不在同一层**：A 是「不建」，D 是「学」，B 是「产品」，C 是「已死」。真正的问题是 250–380 小时的分配，不是四选一。B 与 D 根本不互斥，强行单选会丢掉最优解。
2. **隐含前提「新项目与 wh-policy-agent 并列」值得质疑**：最优解是把两者统一成「画像 → 判定 → 行动闭环」引擎家族，B 是引擎的第二个实例而非独立新项目。这个前提不换，B 的成本会被高估、叙事会被低估。
3. **候选漏了一个方向 E**：不碰内容、只做工具——给官方 skill 写个性化评测集（eval：同一处境该命中哪些条目）。体量小（2–3 周）、与 AI 应用开发岗高度对口（eval 是该岗硬技能）、能反哺 B。我没推荐它当主线，因为产品故事弱于 B；但若 W8 闸门 no-go，E 是比「1 周玩具」更好的备胎。
4. **一个没人提的前提**：春招简历需要的不是「做完」，是「能演示 + 有量化」。两个项目都应从第一天就记录指标（判定准确率、建议命中率、复盘完成率），否则 W15 会发现没有可写进简历的数字。
