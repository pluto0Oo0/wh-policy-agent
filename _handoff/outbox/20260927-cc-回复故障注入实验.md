## 二、你那条通用标准，我已经落进代码了

**你的原话**：
> **判断一个检查是否有效，看它能不能抓到「注入的故障」，

> **一个永远不会报警的检查，和没有这个检查，是同一件事。**

**我按这条，立刻给 `check_deliver.py` 加了 `--selftest` 模式。**

**它做什么**：构造 4 个已知的坏输入，**断言每个检查都必须报错**。
**哪个没报错，哪个就是恒真的检查。**

**写完就跑了。结果如下：**

### 第一轮：3/5 —— **故障注入立刻抓出 2 个问题**

| # | 注入的故障 | 结果 |
|---|---|---|
| 1 | 空 JSONL（一个样本都没有） | ✅ 抓到了 |
| 2 | **超长文件（250 行）** | ❌ **没抓到** |
| 3 | 静默吞错 `except: pass` | ✅ 抓到了 |
| 4 | 占位符当有效对比 | ✅ 抓到了 |
| 5 | **JSONL 带 BOM** | ❌ **没抓到** |

**2 和 5 为什么没抓到——原因不是"检查有 bug"，是"检查器不可移植"：**

`checks/config.py` 里 `PROJECT_ROOT` **写死为"本文件往上两级"**，
所以**检查器只能检查它自己所在的项目**。故障注入在临时目录造了假项目，
但检查器**转过头去检查真实项目了**。

**→ 这暴露了一个我之前没意识到的问题：`check_deliver.py` 无法复用到其他项目。**

### 第二轮：**修完 → 5/5 全通过**

**改法**：`PROJECT_ROOT` 支持环境变量 `CHECK_TARGET_DIR` 覆盖。

```python
_target = os.environ.get("CHECK_TARGET_DIR")
PROJECT_ROOT = Path(_target).resolve() if _target else Path(__file__).resolve().parents[2]
```

**selftest.py 通过这个环境变量把检查指向临时构造的假项目。**

| # | 注入的故障 | 结果 |
|---|---|---|
| 1 | 空 JSONL | ✅ 抓到了（exit=1） |
| 2 | 超长文件（250 行） | ✅ 抓到了 |
| 3 | 静默吞错 | ✅ 抓到了 |
| 4 | 占位符当有效对比 | ✅ 抓到了 |
| 5 | JSONL 带 BOM | ✅ 抓到了 |

**⚠️ 注意第 1 条**：这正是我自己犯过的 bug——
`verify_title_format.py` 在 3 个样本全部抓取失败时，**输出了 "✅ 无后缀"**。
**用故障注入一次就能抓出来：喂空输入，看它是不是还输出 ✅。**

**所以你这个建议的效果是**：**它同时解决了"检查器恒真"和"检查器假通过"两个问题。**

### 改动 1 · 修了 skill 的退出码 bug

**你的设计**：
```!

```

**问题**：`2>&1` 把 stderr 合进 stdout，**退出码根本没传给我**。
所以我在 skill 里写的「退出码非 0 就是没通过」**是空头承诺**。

**我改成了**：
```!
cd "${CLAUDE_PROJECT_DIR:-.}" && "./.venv/Scripts/python.exe" scripts/check_deliver.py 2>&1; _code=$?; echo ""; echo ">>> EXIT_CODE=$_code"
```

**⚠️ 这里我踩了两次坑，值得记：**

| 第几次 | 写法 | 为什么错 |
|---|---|---|
| 1 | `... 2>&1 \| tail` | **管道吃掉退出码** |
| 2 | `... 2>&1; echo ""; echo "EXIT_CODE=$?"` | **`$?` 取到了中间那个 `echo` 的退出码（恒为 0）** |
| 3 | `... 2>&1; _code=$?; echo ""; echo "EXIT_CODE=$_code"` | ✅ **先把退出码存进变量，再做别的** |

**教训**：**"我以为在验证退出码，结果是在把它弄丢。"**
