### 2.2 取值域交集检测已落地（`conditions/loader.py`）

**`FIELD_DOMAINS`**：画像字段的可能取值域（SPEC §2.3 目前没有，**待补**）。

**`check_value_domain(cond)`**：条件 `value` 与取值域**无交集 → 抛异常**（**fail 不 warn**）。

**为什么是 fail**：不相交 = 这条**永远不可能 PASS**，不是"可能有问题"，是"确定是错的"。

**一个刻意的例外**：**计算类跳过检测** —— 它的 `field`（如 `rent`）是**输出字段**，
拿它去查画像取值域会报一堆假警报。

### 2.3 故障注入：**复现 `_03` 的原写法**

这是我认为本轮最该看的一条：

```
✅ 复现 _03 原写法（取值域不相交）        期望抛异常 / 实际抛异常
✅ 对照：同字段取值域有交集（不该误报）     期望通过 / 实际通过
✅ 对照：计算类的输出字段不该被误报        期望通过 / 实际通过
```

**如果这条检测当初就在，`_03` 会在第一次加载时被抓到**，
不用等"偶然跑了一次真数据"才暴露。

**两个对照用例是刻意的**：防止"检测太严，把正常条件也拦了"（假警报）。

## 三、🔴 我在实现过程中犯了一个 bug，而且**违反了我自己写的注释**

**症状**：`_11`（`has_dependents exists`）和 `_13` 判 **FAIL**，导致整体 `INELIGIBLE`。

**真相**：那两个字段**根本不在画像里** —— 「**字段不存在**」被我的实现当成了「**值为 False**」。

```
if cond.op == "exists":
    value = profile.get(cond.field)      # 字段不在 → None
    return (PASS if value not in (None, "") else FAIL)   # → FAIL  ← 错
```

**正确行为是 UNKNOWN + 追问那个字段。**

**为什么这条特别该记**：我在 `eligibility.py` **模块开头的 docstring 里
专门写了「UNKNOWN 不是 INELIGIBLE」**，结果**在同一文件的 `exists` 分支上违反了它**。

> **把原则写进注释，不等于在代码里执行了它。**
> 这和 `CLAUDE.md` 第 10 条那次（写完"要自检"，当天就违反）是同一个结构：
> **原则是"知识"，不是"动作"。**

**已修**。修完后：

```
verdict        : UNKNOWN
missing_fields : ['has_dependents', 'qualification_valid', 'wants_short_stay']
逐条：01-06 PASS / 07 UNKNOWN(ambiguity) / 08 PASS / 10 N/A(老轨道) / 11-13 UNKNOWN
```

**这个 verdict 是对的**：没有一条 FAIL，有三条信息不足 → `UNKNOWN` + 明确列出要补什么。

## 四、两处「写死数字」的断言失效 —— **同一个毛病，一天内两次**

| 位置 | 写死了什么 | 失效原因 |
|---|---|---|
| `loader.py` 断言 1 | `len(conds) != 9` | golden set 涨到 13 条后**断言过期** |
| `eligibility.py` 故障注入 | `{"06","07"} <= unknown_ids` | `_03` 拆两条后**全部重编号**，断言过期 |

**两次的失效原因都是"断言过期"，不是"代码错了"** —— 而**失效的表现和"真出错"一模一样**（都是 ❌）。

**已修法**：
- `loader`：改成具名常量 `EXPECTED_CONDITION_COUNT`（下次改数据时会看到它、需要主动改它）
- `eligibility`：改成**按 `field` 反查**受影响的条，不写死编号

**建议记进教训清单**（和"用标记定位内容"那条同类）：
> **测试里不要写死"数据的编号或条数"** —— 它会随数据演进静默过期，
> 而过期的断言**看起来和真错误一样**。改成"按语义反查"（按 field、按类型）。
