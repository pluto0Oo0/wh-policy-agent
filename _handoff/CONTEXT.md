## 8. 已确立的流程与工具

**交接区**：`_handoff/{inbox, outbox, done}` + `README.md`。命名 `YYYYMMDD-来源-主题.md`，优先级写入文件名（P0/P1/P2）。

**inbox 文件结尾三段式**（缺一不可）：
1. 请你查证（我没验证过的）
2. 我已实测验证过，**可直接采信**（防 CC 重复劳动）

## 10. 教训清单（高价值，都是踩出来的）

| # | 教训 |
|---|---|
| 1 | **栏目停更 ≠ 政策失效**。作为"发现新政策"的源不合格，作为"获取原文"的源可能合格（wb 曾判错，已纠正） |
| 2 | **布尔硬指标失败时，必须再查一次失败原因**——「0 命中」可能是源不对，**也可能是翻页不够**（78 号文在第 10 页） |
| 3 | **判断一个检查是否有效，看它能否抓到注入的故障**，不是看它正常运行会不会全绿。**永远不报警的检查 == 没这个检查** |
| 4 | **检查器有两类 bug**：假警报（误报）和**假通过（漏报）**。**后者更危险，因为它不会引起怀疑** |
| 5 | **检查器自身会扫到自己**——`changed_py_files()` 要排除 `scripts/checks/` |
| 6 | **`2>&1` 会吞掉退出码**；`echo` 也会重置 `$?`。正确做法：`cmd; _code=$?; echo "...=$_code"` |
| 7 | **静默监控必须有心跳**——否则"在跑"和"死了"无法区分 |
| 8 | **宁可匹配失败（有可见报错），也不要匹配错**（CC 删掉写死兜底路径的教训） |
| 9 | **「抓到东西 ≠ 抓对了东西」**——CC 自己写进 CLAUDE.md 却没做到的话 |
| 10 | **转述会丢信息**：进度汇报写「办公厅 2026 年（全部）」，实测是 2026:20/2025:23/2024:2 |
| 11 | **「长度」类判据在"错误页返回完整渲染页面"的站点上必然失效**——失效页 189,913 字符，**比正常页（116,671）还长**。**优先用结构判据（容器存在性）和布尔判据，不要用数值阈值** |
| 12 | **给判据时必须给"失效时的实际取值"，不能只给逻辑描述**——wb 说「core 为空」，实际失效时 title 是纯站点名、**根本没有分隔符可去**，core 非空。**判据必须配实测样本，否则会造出假通过** |
| 13 | **「列表里扫不到」≠「不存在」——这是第二次出现了**（① 78 号文在第 10 页；② 78 号文官方解读 URL 有效且 200，但不在 `rsj` 可见的 16 条列表里） |
| 14 | **审查者自己也会成为假通过的源头**——第 12 条那个 bug 是 wb 引入的。双向纠错不等于"只有 CC 会被纠错" |
| 15 | **监控器失效有第三种形态：「根本没接上」**——比假通过更彻底，且**症状与"一切正常"完全一样**。验证一个监控器是否生效，**第一步永远是确认它被挂上了**；这一步在本项目被跳过两次（09-26 查了脚本逻辑却没查注册状态） |
| 16 | **配置类改动必须确认"生效"，不是确认"写进去了"**——`settings.json` 文件层面完全正确，但 hooks 在 session 启动时快照，**不重启/不跑 `/hooks` 就从未生效**。"文件对了"和"运行起来了"是两件事 |
| 17 | **修复时要顺带扫一遍同类模式，不能只修复现到的那一个**——`session-check.js` 修好的位置下面 34 行就还有一个空 `catch`；全 4 个脚本 13 个 catch 里 8 个静默。**只修一个点 = 教训没学到** |
| 18 | **"方向存疑"不能作为"留着已知 bug 不修"的理由**——修已有缺陷 ≠ 堆新代码。要么停工待定（那更该把遗留 bug 清干净），要么继续做（那也该修）。**只停一半 = 取两个选项的缺点之和** |
| 19 | **止血类动作不要"等指令"**——`git init` 2 分钟、零风险、可逆；而代码只有磁盘一份这件事的风险与日俱增。**在止损问题上，"等批准"本身就是风险** |
