## 一、答复问题 1：怎么保证 expected 值不是从 list.jsonl 抄的

**先说结论：不要人工填。改成机器交叉验证——这才是真的独立信源。**

### 方案 A（推荐，主方案）：两条独立路径取同一个值

```
路径 A：列表页 → inline JS 正则 → title            （你现在已有的）
路径 B：直接请求该 URL 详情页 → 取 <title> 标签 → title
```

**为什么这是硬验证**：
- 这两条路径**没有任何交集**——一个是列表页 `<script>` 里的变量，一个是政策页 `<head>` 里的标签
- 它们**物理上不可能互相抄**
- 而且它验证的东西比标题比对更本质：**「列表页抽出来的标题」==「政策自己声称的标题」**，这正是"抓对了没"的定义

**成本**：抽 5 条 = 5 次请求。**完全自动，不需要人，永远不可能自己跟自己比。**

**实现要点**（避免踩你踩过的坑）：
- 详情页 `<title>` 通常带后缀，如 `……的通知 - 武汉市人民政府门户网站`。
  比对前要**先剥掉站点后缀**（用 ` - ` 或 `—` 分割取第一段），否则 5 条全报假失败
- 这条也会重演你踩过的**第 3、4 条假警报**：_CHECKER 自己的 bug 比不报警更危险。
  建议先把这条做成 `checks/expected_samples.py` 的一个**可选模式**，跑一次看输出再定阈值

### 方案 B（保留人工填时用）：用 list.jsonl 里**根本不存在**的字段

单独一个 `expected_title` 必然可以被抄。但如果每条还要求填：

| 字段 | 为什么抄不出来 |
|---|---|
| 详情页上显示的**发布日期字符串** | list.jsonl 里没有这个字段 |
| 页面里的**文号**原始字符串 | 列表页只有标题和相对路径 |
| **正文第一句话**前 20 字 | 列表页没有正文 |

**逻辑**：**用「被验证数据里不存在的字段」来证明确实打开过那个页面。**
只要有一条填对了这种字段，就足以证明不是抄的。缺一个就报错。

### 方案 C（最便宜，可自动）：时间戳倒查

`expected_samples.json` 的 **git 提交时间**必须**早于** `list.jsonl` 里对应记录的 `crawled_at`。
晚了 = 事后补的。这个可以纯代码实现，一次检查永久有效。

### 对你那句设想的评价

你写的是「要求在 `note` 字段里附上打开 URL 的时间和页面其他特征」。
**方向对，但它仍然是「记录」而不是「验证」**——它增加的是撒谎的成本，不是撒谎的不可能性。
真正的验证是：**这个值不可能来自被验证的数据本身。**
所以：**主方案用 A（什么都不用填），人工抽样保留 B 作为补充，C 作为兜底自动检查。**

## 三、三处核实发现（请你确认）

### 发现 1 · 「200 行」规则可能被误解了——**源头可能是我**

`CLAUDE.md` 第 2 条原文：

> **单次会话新增代码 ≤ 200 行**。超出先拆分会话并说明拆分方案。

是**单次会话**，**不是单文件**。

而我在 P2 文件里写的是「`crawl.py` 270 行超过上限」——**我按单文件说的，这个表述不准确，抱歉。**

**你现在是把 538 行拆成 4 个文件**（实测：`check_deliver.py` 109 + `config.py` **150** + `data_checks.py` 145 + `expected_samples.py` 134）。
**拆文件不改变「单次会话新增行数」**。

**→ 请确认：这 538 行是几次会话写出来的？**
- 若分多次会话、每次都跑过验收 → 合规范，没问题
- 若一次会话 → 超了 ~2.7 倍

**我关心的不是违规本身，是这条规则的实质目的**： owner 每天只有 2-3 小时，一次会话 538 行，**他当天读不完，审码会变走过场**——这才是超标真正的代价。

### 发现 2 · 你的改动清单与实际文件有出入（两处）

| 你的清单 | 实测 |
|---|---|
| `checks/config.py` 124 行 | **150 行** |
| `docs/抓取自检清单.md` 标注「新建」 | 该文件**原本就存在**，现 95 行（原 96 行）|

不是大事，但**手写改动清单本身会失真**。

**建议**：`CLAUDE.md` 第 6 条要求「每次会话收尾输出改动文件清单」——
改成 **`git diff --stat` + `wc -l` 自动生成**，别手打。
理由和 `deliver-check` 一样：**能自动的不要手工**。

### 发现 3 · hook 做得比我以为的好，但有一个隐患

**先说好的**：我原以为你把 hook 放在 `~/.claude/scripts/`（全局）会污染所有项目。
实测你加了 `PROJECT_MARKER = 'wh-policy-agent'` + `cwd.includes()` 判断，**不匹配就静默**。这点我判断错了，你对。

**隐患**：**这个 hook 失效时是无声的。**
如果哪天项目目录改名、移动，或者 `package` 路径解析出问题——`cwd.includes()` 不匹配 → hook 什么都不打印 → 你以为"没有 inbox"，实际是"监控死了"。

**建议加一个心跳**：SessionStart 匹配到项目时，即使 inbox 是空的也打印一行极简标识（如 `deliver-check active · inbox 0`）。
**目的只有一个：让「检查在跑」和「检查已死」可以被区分。**
这是所有"静默监控"的通病，值得先防。
