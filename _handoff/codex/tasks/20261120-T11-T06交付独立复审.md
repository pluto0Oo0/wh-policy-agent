## 二、CC 已定位的核心问题（你要独立复核，不要直接采信）

### 2.1 现象

T06 完成报告第 311-367 行，`python -m src.engine.eligibility` 的**验收输出**长这样：

```
verdict        : INELIGIBLE
missing_fields : []

逐条：
  01  PASS     年龄不满45周岁（研究生不受年龄限制）的高校毕业生凭毕业证书在市内落户
  ...
  01  UNKNOWN  通过大学毕业生租赁房租赁资格审核的
  02  FAIL     意向租住区为硚口区          ← 这是硚口区的政策
  01  UNKNOWN  已通过人才租赁房资格审核
  02  FAIL     意向租住区为江岸区          ← 这是江岸区的政策
  ...
```

**判定的是 78 号文（`t20220608_1983869`，13 条条件），但 reasons 里出现了全部 20 个政策、52 条条件。**
其中 6 条区级「意向租住区为 X 区」判 FAIL → **verdict 被压成 INELIGIBLE（不符合）**，
→ `missing_fields` 被清空（SPEC 规定只在 UNKNOWN 时输出）
→ **「信息不足」被判成了「不符合」。**

### 2.2 根因（CC 已定位到行，但你要自己复核一遍）

| 位置 | 代码 | 作用 |
|---|---|---|
| `src/engine/eligibility.py:423` | `def _load_fixtures()` | **把全量 52 条条件传给 `check_eligibility`，没有按 `doc_id` 过滤** |
| `src/engine/eligibility.py:381` | `if FAIL in statuses:` | **FAIL 优先于 UNKNOWN** → verdict = INELIGIBLE |
| `src/engine/eligibility.py:409` | `"missing_fields": missing if verdict == VERDICT_UNKNOWN else []` | verdict 不是 UNKNOWN 就清空 |

### 2.3 为什么这不只是「测试写错了」

**Codex 的处理方式是「方案乙」**（见完成报告「不确定的地方」第 2 条）：

> 「v4.1 加入区级硬条件后，原自测把全部政策条件混在一起跑，示例画像会出现跨区 FAIL，
> 整体变成 INELIGIBLE；而 SPEC 规定 `missing_fields` 只在 UNKNOWN 时返回，
> 所以旧断言『`market_rent` 必须在全量结果的 `missing_fields` 里』会失败。
> **我把它改为只对单个计算类条件测 `market_rent`。产品判定语义没有改。**」

**CC 认为这个处理不成立**，理由：

1. **缺陷本身没消除。** `check_eligibility(conds, policy_meta)` 收到**不属于自己的**条件时，
   **既不报错也不过滤，而是静默算进去**。
2. **其他调用方已经自己绕过了它**：
   - `src/cli.py:246` — `conditions = [c for c in conditions if c.doc_id == policy["doc_id"]]`
   - `scripts/evaluate.py:76` — `conditions = grouped.get(policy_id, [])`
   → **也就是说，只有引擎自测这一处把全量传进去了。**
   → **如果没人跑 `python -m src.engine.eligibility`，这个缺陷可以一直藏着。**
3. **断言0 把缺陷固化成了「正确行为」。**
   `eligibility.py:488` 打印「✅ 断言0：52 条条件全部出现在 reasons 里」——
   这条断言现在**要求**引擎把 20 个政策的条件都算进 reasons。
   **一旦将来引擎正确地按 doc_id 过滤，这条断言反而会失败。**
4. 这是 CLAUDE.md 第 10 条典型的「程序不报错但结果是垃圾」。

> **「收窄测试」和「修引擎」哪个才是正解？**
> 给出你的判断 + 依据。
