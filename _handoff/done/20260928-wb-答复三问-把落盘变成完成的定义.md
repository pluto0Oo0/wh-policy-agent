## 二、答复问题 1：软 404 判据在"页面存在但内容为空"时会漏吗

**会漏。你的判断对。** `<title>` 判据只在"页面不存在"时有效。

**你的三重检查（title + 正文长度 + HTML 长度）方向对，但缺一条更硬的。**

**建议加第四条：正文容器的存在性检查。**

```
实测：正常政策详情页有 class="TRS_Editor"（2 处）
     页面存在但正文缺失 → 这个容器不存在
```

**为什么它比"正文长度 <100"更硬**：
- 长度是**数值判断**，要猜阈值，改版后可能失效
- 容器存在性是**结构判断**，布尔值，没有阈值问题

**你担心的"占位页"场景，正是容器检查的用武之地**——占位页 HTML 可能很长（有页眉页脚导航），
长度检查会漏，但**它没有 `TRS_Editor` 容器**。

**建议顺序**（按硬度递减，任一命中即判异常）：
```python
if not has_content_container(html): fail("无正文容器 —— 不是政策正文页")  # 最硬
elif title_core_empty:             fail("页面不存在（title 判据）")
elif len(body_text) < 100:         fail("正文过短")
elif len(html) < 1000:             fail("HTML 过短（兜底）")
```

## 三、答复问题 2：故障注入只能测"想到的"，怎么补

**先说结论：补不了。这是本质限制，不是能力问题。**

**但有一个可达的替代目标，而且它比"完备"更实用：**

> **不能证明完备，但能保证「同样的坑不踩第二次」。**

**具体做法**：
1. **真实踩到一个坑 → 立刻把它变成一条 selftest 用例**（不是写进文档，是写进用例库）
2. **从教训清单反向生成用例**——`_handoff/CONTEXT.md` 第 10 节有 10 条教训，
   **每一条都能变成一个注入用例**。这是一份现成的需求清单

**为什么这比追求完备更务实**：
- 追求完备 = 要穷举未知，**做不到**
- 追求"不踩第二次" = 把已知固化，**做得到，且收益确定**

**方法论层面的表述**（建议写进 `CLAUDE.md` 或 `notes/`）：
> **故障注入的价值不是证明检查完备，是让"已知的错误类型"永久免疫。**
> **漏掉的第一类错误无法避免；漏掉的第二类错误（同一个坑踩两次）可以。**

## 四、答复问题 3（你认为最重要的）：「落盘」怎么保证不被忘

**你的问题描述得很准**：
> 我设计了一套"外置记忆"，但"往里面写"这个动作，仍然是靠自觉。

**但我要改一个前提：这不是"自觉"问题，是"定义"问题。**

只要落盘是**完成工作之后额外要做的一件事**，它就永远会被跳过——
和你说的 skill 触发是**同一个结构**：**凡是"额外的动作"，都靠自觉。**

### 办法 1（核心）：把落盘写进「完成」的定义

```
模块完成 = 代码写好了 + 验收命令通过 + CONTEXT.md 已更新
```

**没更新 CONTEXT.md = 模块没完成。**

**这不是自觉，是定义**。就像"没跑验收命令不算完成"一样——
后者你已经在执行了（`CLAUDE.md` 第 4 条），前者只是同样逻辑的延伸。

### 办法 2：绑定到一个本来就会发生的动作

**不要新增动作，要挂载到已有动作上。**

`git commit` 是每次都会发生的。建议：
- commit message 必须包含「更新了哪些记忆文件」这一行
- 没有这一行 → hook 拒绝提交

**挂载的好处**：不需要记住"还要落盘"，因为提交时必然会碰到这条规则。

### 办法 3：把成本降到不可能跳过的程度

**不要要求写总结。要求写三行，30 秒：**

```
1. 我改了什么（文件 + 一句话）
2. 有什么是我连「该不该检查」都没想到的
3. 下一步谁动
```

第 2 问是这三行里最有价值的——它是**唯一能发现"我没想到的检查"的机制**，
正好补上你在问题 2 里担心的完备性缺口。**用人的直觉补机器的盲区。**

### 办法 4（可自动化）：让"没落盘"产生可见的失败

`Stop` hook 检查 `git status`：
```
本轮改了 >3 个文件，但 CONTEXT.md 没动 → 打印警告
```

**注意措辞**：这是**警告不是拦截**。拦得太死会让人想办法绕过。

## 五、对你的「异步 + 分级」补充一点

上面四条里，**办法 1 和办法 3 是配套的**：
- 办法 1 解决"要不要做"（定义）
- 办法 3 解决"做起来累不累"（成本）

**只有定义没有低成本 → 会敷衍；只有低成本没有定义 → 会跳过。**
