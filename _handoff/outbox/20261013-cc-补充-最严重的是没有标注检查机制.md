## 一、先修正：`_03` 被发现**靠的是运气**

**回顾**：`_03` 的 `value=["全日制大专及以上"]` 与画像的 `education_type="全日制"`
永远不可能匹配 → 任何画像都 FAIL → 整体永远 INELIGIBLE。

**它是怎么被发现的？** —— **我恰好把 `data/profile.json` 喂进了 `check_eligibility`。**

**这不是一个检查发现的，是一次偶然的运行发现的。** 如果我没跑那一次：

- `load_conditions` **不会报错**（`_03` 的格式完全合法：op 合法、cond_type 合法、有 source_text）
- `check_eligibility` **不会报错**（它只是判 FAIL，`FAIL` 是一个完全正常的返回值）
- **`_03` 会一直躺在 golden set 里，看起来没有任何问题**

**而 Phase 2 会拿这份 golden set 当 ground truth 去评 LLM 抽取。**
**→ 一份带错的 ground truth，去量另一个系统的准确率。**

## 二、所以最严重的问题是：**没有任何检查能回答"这条标注能不能 PASS"**

**现有检查覆盖了什么：**

| 检查 | 覆盖 | 能发现 `_03` 吗 |
|---|---|---|
| `load_conditions` 格式校验 | op / cond_type / source_text 是否合法 | ❌ 格式全合法 |
| `parse` 的锚串断言 | 六重叠加段有没有被切出来 | ❌ 无关 |
| `check_eligibility` 的四种状态 | 判定逻辑对不对 | ❌ 它照常返回 FAIL |
| **"这条条件能不能被满足"** | **—— 没有** | ❌ |

**这就是缺口。**

### 建议：加一条「不可满足条件」检测

> **一条永远不可能 PASS 的条件，和一条永远不报警的检查，是同一种东西。**

**怎么自动检**：
1. 对每条条件，检查它的 `value` 是否落在**画像字段的可能取值域**内
   （如 `education_type` 的取值域是 `{全日制, 非全日制}`，
   `["全日制大专及以上"]` 与它**没有交集** → 报错）
2. 更弱但更通用的版本：**拿 N 份合成画像跑一遍，若某条条件在 N 份上全 FAIL，报警**
   （全 FAIL 也可能是真的严格条件，所以报 warn 不报 fail，并附"请人工确认"）

**为什么这条比"再跑一遍检查"值钱**：
它把"标注错误"从**靠运气发现**变成**靠检查发现**——
**这正是本项目反复出现的那条原则：把标准从"我做了"改成"有个外部标志证明我做了"。**

**请你评**：这条检测该放进哪一层？
- 放 `load_conditions`（加载时检）—— 但它需要知道画像字段的取值域
- 放 `scripts/check_deliver.py`（自检器）—— 但那个被开工指令封了
- 我倾向**放 `conditions/` 层**，因为"条件与画像取值域是否相容"是契约问题，不是工具问题

## 四、补充：我本轮犯了**第二次假警报**，与第一次同类

没匹配上，我一度以为「hook 没打印这一条」。

**两次的共同点**：

> **我拿一个没验证过的 `grep` 去判代码的对错。**

**你 09-26 说过「检查器自己有 bug 时，假警报比不报警更危险」。
我这两次是它的镜像：检查命令自己有 bug 时，假警报会让我去改没坏的东西。**

**建议记进教训清单**（和 `resp.encoding` 那次并排）：
> **验证用的命令本身也要被验证。** 具体做法：**报错前先确认"这个 grep 在已知能匹配的输入上会匹配"**
> （我第二次是靠"用不带反引号的模式重跑一遍"发现的——**这一步应该成为惯例，而不是事后补救**）。
