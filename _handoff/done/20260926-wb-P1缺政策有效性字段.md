# P1 · SPEC 缺「政策有效性状态」字段——当前设计无法回答「这条还有效吗」

> **来源**：外部审查者（wb） · 2026-09-26
> **起因**：所有者连续两次质疑——「2022 年的文件现在查对吗」「找到的都是旧的不是误人子弟？」
> **性质**：**建议不是命令**（交接区规则 2）
> **优先级**：P1 —— 不阻断当前抓取，但**必须在 Phase 1 契约定稿前处理**，否则后期返工

**依据标注**：【看过原始材料】`docs/SPEC.md` §1.5 / §2.1 / §7 +【检索所得】官方信源验证

---

## 一、所有者的担心成立，但问题定位要换

担心的内容对，担心的对象错了一半。

| 担心的 | 是不是真问题 |
|---|---|
| 「系统给旧答案」 | ❌ **不是核心问题**。政策文件的默认状态是长期有效，不因年份增长自动失效 |
| 「系统给了已失效的答案，且显示不出来」 | ✅ **这才是真问题** |

**核心区分**：**「最新政策」和「现行有效政策」是两回事。** 本项目要的是后者。

## 二、为什么「政策旧」本身不是风险（实测佐证）

`武政办〔2022〕78号`（2022-06 印发）在 2026 年仍是现行规则：

| 日期 | 官方动作 |
|---|---|
| 2026-09-07 | 媒体报道仍在按其条款描述人才租赁房优惠（博士免 2 年 / 硕士 1 年 / 7 折） |
| 2026-08-28 | 市人社局提案答复称「我市**现行**人才安居政策」 |
| 2026-08-25 | 洪山区住更局按该文件答复群众咨询 |
| 2026-07-13 | 市住房和城市更新局按该文件答复群众咨询 |

**政策不像新闻。** 一份规范性文件被明令废止前，它 2022 年和 2026 年的效力是一样的。
「这份文件是 2022 年的」不构成风险，**「这份文件已被废止而我没查」才构成风险。**

## 三、真正的缺口：SPEC §2.1 里没有任何字段能表达「有效性」

现有字段：`doc_id / url / title / doc_number / publish_date / region / template_family / content / crawled_at`

**缺三样**：
1. 这条政策**是否现行**（现行 / 已废止 / 部分失效 / **未核实**）
2. **最后一次核实有效性的时间**
3. 若已废止，**被哪份文件替代**

**后果推演**（这是所有者担心的具体形态）：
> 2027 年 6 月面试官装一个毕业生，系统答「你可以享受 X 优惠，依据武政办〔2022〕78号」。
> 但那份文件在 2027 年 3 月已被新文件替代。
> **系统全套自检都是绿的**——数据格式正确、原文摘录准确、引用无误——**只有答案是错的。**

**这正好是 Project 自己的红线**：「程序不报错，结果是垃圾」。

## 四、建议：给数据契约加四个字段

**改什么**：`docs/SPEC.md` §2.1 `policies.jsonl` 增加：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `policy_status` | str | ✅ | `现行` / `已废止` / `部分失效` / **`未核实`** |
| `status_verified_at` | str | ✅ | 最后一次核实有效性的日期（ISO 8601）|
| `status_evidence` | str | ⬜ | 核实依据（如"2026-08-28 人社局提案答复仍在引用"）|
| `superseded_by` | str \| null | ⬜ | 被哪份文件替代（doc_number 或 url）|

**为什么每个都要**：
- `policy_status` 必须有 **`未核实`** 这个值——原因和 SPEC §2.2 `ambiguity` 的设计一致：**宁可显式承认不知道，不要默认成立**。缺核查就填「未核实」，判定层按 §3.5 的规则处理。
- `status_verified_at` 用来做「过期复核」：`crawled_at` 只记录抓取时间，**不代表有效性核实过**。
- `status_evidence` 让核实可被追溯、可被别人反驳——这是 `D10`「第五步对比是真对比」的同款思路。

## 五、判定层怎么用它

**改什么**：`docs/SPEC.md` §2.4 返回值与 §3.6 `check_eligibility` 增加一条规则：

> `policy_status == "已废止"` → 该政策**不参与判定**，直接跳过
> `policy_status == "未核实"` → 判定结果带**显式警告**，而不是静默给出 ELIGIBLE

**为什么**：这跟 §3.5 已有的设计完全同构——
`ambiguity` 非 null 时返回 `UNKNOWN` 并追问，**那是对「条款模糊」的处理；这是对「政策本身可能过期」的处理**。两者是同一个原则的两处应用，实现成本很低。

## 六、顺带：这个担心可以反过来变成卖点

**所有者问的这句「2022 年的文件现在还有效吗」，就是真实用户的第一反应。**

如果系统的输出长这样：

```
依据：武政办〔2022〕78号（2022-06-07 印发）
状态：现行有效 · 最后核实 2026-09-26
核实依据：2026-08-28 市人社局答复仍在引用
原文摘录：「……不高于市场租金的70%……」
```

**它同时回答了「我能不能享受」和「这条还作不作数」两个问题。**
后者恰恰是市面上所有政策问答类产品都没做的事（调研报告 §12.4 已论证）。

**→ 这个质疑不是在打这个项目，是在给这个项目指一个别人没做的点。**

## 七、我不确定的点

1. 「保障性租赁住房」（2026-04-24 新政）与「人才租赁房」（78号文）**是不是两条并行轨道** —— 未核实。若是两条，`policy_status` 必须按各自的轨道分别判定，不能混。
2. 没有找到 78 号文的废止文件，但**「没找到」不等于「不存在」**。建议把这个核实动作做成数据检查项，而不是一次性人工判断。
3. 我不知道 Phase 1 结束时（约 2026-11）政策是否会变——**所以 `status_verified_at` 比一次性核实更重要**。
