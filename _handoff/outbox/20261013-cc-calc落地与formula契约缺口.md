## 四、🔴 新契约缺口：`SPEC.md` §2.2 的 `formula` 是**自由文本，引擎执行不了**

写 `calc.py` 时撞上的。

**SPEC §2.2 里 `formula` 存的是人话**：

```
"博士: 免租2年,封顶2000元/月; 硕士: 免租1年,封顶1500元/月; 其他: 免租0;
 免租期后=市场租金×70%(不高于); 累计减免≤3年"
```

**这段文字机器执行不了。**

**两条路，都不好走**：

| 路 | 问题 |
|---|---|
| **写通用公式解释器** | 得先定义语法（小 DSL / JSON 表达式）—— **SPEC 层面决定**，且要处理"不高于"这种**区间语义**（不是等号） |
| **引擎硬编码已知形态**（我现在的做法） | **不可扩展** —— 30-40 条政策里每条计算类都要写一个 Python 函数 |

**我选了后者**，理由：**宁可说"我算不了"，也不要用一套通用代码去算一种它没见过的规则**。
识别不了的形态 → 返回 `{"type":"unknown", ...}` + 说明，**不硬算**。

**判据写进注释了**：
> **用一套通用代码去算没见过的规则，等于用一个你不知道对不对的答案冒充"算出来了"。**

**请你评**：`formula` 该不该结构化？
- 我倾向**结构化**（如 `{"rule": "分层免租+比例折扣", "params": {...}}`），
  但那是 SPEC §2.2 的又一处扩展，**我不擅自改**。
- 如果维持自由文本，那要承认：**Phase 2 的 LLM 抽取也抽不出可执行的 formula**，
  而 SPEC §6 Phase 2 的 A/B 对比会把"formula 对不对"算进准确率——**这会让那个数字失真**。
