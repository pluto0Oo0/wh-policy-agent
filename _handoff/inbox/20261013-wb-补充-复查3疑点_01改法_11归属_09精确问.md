```
原 _01: age < 45
分层后: if education in {硕士,博士}: 跳过; else: age < 45
```

**SPEC §2.2 的 Condition 数据结构没有"依赖字段"或"豁免条件"字段**。你怎么改的？

## 疑点 2 · `_11` 删掉后"配偶随迁"放哪——我上封说"放 where_to_apply"不够精确

我上封建议把"配偶及未成年子女可随迁"放进 `where_to_apply`。**复查发现这个建议不精确**：

SPEC §2.4 的 `where_to_apply` 当前字段是 `office / phone / source_text`——**这三个都放不下"可随迁人员"这条信息**。

| 字段 | 能放吗 |
|---|---|
| `office` | ❌ 是受理部门地址 |
| `phone` | ❌ 是电话 |
| `source_text` | 勉强（原文摘录里有这句），但它是"抄原文"不是"结构化字段" |

**所以 _11 删除后，"配偶随迁"信息没有天然归属**。需要选一个：

| 选项 | 说明 |

| A | `where_to_apply` 加 `notes` 字段（"申请注意事项"，配偶随迁放这里） |
| B | 新建一个"申请须知"类字段（但 SPEC 没有） |
| C | 本期不处理，CONTEXT 记一笔"78号文含配偶随迁权益，本期不做结构化" |

## 疑点 3 · `_12` 的 `qualification_valid`——我上封说"判定中间状态"不准确

我上封说 `_12`（在资格有效期内）的 `qualification_valid` 是"判定引擎的中间状态"。**复查发现这个说法不准确**：

资格是否在有效期内，**既不是画像静态属性（用户自带），也不是引擎能算出的中间状态**——它是**外部状态**（需要查政务系统或用户自报）。

**所以 _12 实际上是"永远不可自动判定"的**——它的值永远来自用户自报或外部查询。

**本期处理**：标 UNKNOWN + 追问（"你的安居资格是否在有效期内？"）是对的。但要在 CONTEXT 记一笔：**_12 是"外部依赖型条件"，永远需要用户输入，不是引擎能自动判的**。这影响 Phase 2 的 A/B 对比——LLM 抽取时也会抽到这条，但它的"可判定性"和其他条件不同。

## 疑点 4（强化上一封的 _09 问题）· _09 是计算类，产出是 amount 不是 PASS/FAIL

上一封我问"_09 的判定状态是什么"。复查后我要**更精确地问**：

`_09` 是计算类（六重叠加），**它的产出语义和其他条件不同**：

| 条件类型 | 产出 |
|---|---|
| 资格类 | PASS / FAIL / UNKNOWN |
| 计算类 | amount（金额）或 None（算不出） |

**所以对 CC 的精确问题是**：
1. `_09` 在 `reasons` 数组里**有没有出现**？
2. 如果有，它的 `status` 是什么？（PASS？还是另有处理？）
3. `amount` 字段有值吗？（SPEC §2.4 返回值里有这个字段）
4. 如果 `_09` 没进 reasons，**是 `check_eligibility` 跳过了计算类**吗？

**第 4 个是最严重的**——如果计算类被 check_eligibility 跳过，那 verdict=UNKNOWN 可能是**假 UNKNOWN**（看起来是"信息不足"，实际是"计算类根本没进判定流程"）。
