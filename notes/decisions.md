### D01 · 不建向量库，用 BM25 + 元数据过滤

- **日期**：2026-09-24
- **结论**：Phase 1 用 `BM25 + 元数据过滤`，不建向量库。
- **为什么不选另一个**：
  1. 语料只有 80-150 条（安居类 MVP 30-40 条），向量检索收益趋近于零
  2. 文号类查询（"武政办〔2022〕78号规定了什么"）必须精确匹配，BM25 远优于向量
  3. 判定要输出"依据哪一条"，元数据过滤比语义相似更可控
- **代价是什么**：口语化查询（"我毕业两年了能租便宜房子吗"）召回会差。若 Phase 2 数据显示召回是瓶颈，再评估是否补向量召回。
- **对应面试问题**：「2026 年模型都 1M 上下文了，为什么还要 RAG，全塞进去不行吗？」  
  → 答：检索不是为了"塞不下"，是为了"要结构化"。全塞进去也得对每条抽条件，成本更高、错误率更高、"抽漏了哪条"不可控。

### D02 · 判定用纯代码，不用 LLM

- **日期**：2026-09-24
- **结论**：`check_eligibility` 和 `calc_amount` 是纯 Python，不调任何模型。
- **为什么不选另一个**：可判定的事不交给模型。比大小、算公式是确定性问题，LLM 只会引入不确定性。LLM 负责"从文本抽条件"（Phase 2），不负责判定。
- **代价是什么**：条件必须结构化，所以第 8-10 周的人工标注不能省。这是有意的——用标注成本换判定可靠性。
- **对应面试问题**：美团"Agent 输出的 JSON 有时不对，怎么做 Schema 校验和重试"；凌脉"工具调用前如何校验参数，避免模型传入错误或危险参数"。

### D03 · 条件必须带 `applies_to_cohort`（人群分层）

- **日期**：2026-09-24
- **结论**：每条条件带适用人群分界字段，判定时先确定用户属于哪个 cohort。
- **为什么不选另一个**：**"取最新版本"是错的。** 实测存在合法的"老人老办法"双轨——2022-06-07 前留汉的按武房规〔2018〕2号（毕业 3 年内 + 武汉户籍），之后按武政办〔2022〕78号（毕业 6 年内 + 社保）。取最新会让一整类人拿到错误答案。
- **代价是什么**：数据结构变复杂，标注时每条都要判断 cohort，人工成本上升。
- **对应面试问题**：「你的系统怎么处理政策版本冲突？」→ 这个答案能直接区分"真做过"和"套教程"。

### D05 · 列表页数据在 inline JS 里，不能用 HTML 标签解析

- **日期**：2026-09-24
- **结论**：`szfwj` 列表页的解析必须用正则提取 `var url = "./...shtml"` + 紧随的 `title = "..."`，不能用 `find_all("a")`。
- **为什么不选另一个**：实测该页 246 个 `<a>` 标签中**只有 3 个含 `.shtml`**，且都是页面框架链接。真正的政策列表包在每条记录的 inline `<script>` 里。
- **代价是什么**：正则比 DOM 解析脆弱——页面结构一变就失效。**必须加"抓到 0 条就报错"的保护**，否则会静默返回空列表。
- **对应面试问题**：「爬虫遇到页面改版怎么办？」  
  → 答：① 抓取数量做断言（少于阈值直接报错，不静默通过）；② 保存原始 HTML 到 `data/raw/`，改版后可用历史数据回归测试解析逻辑。

### D06 · 做「指路」不做「引导申请」

- **日期**：2026-09-24
- **结论**：判定结果附上政策原文里的「受理部门及联系方式」，但**不涉及任何申报引导、材料代填、流程代办**。
- **为什么不选另一个**：
  1. 引导申请会让项目**性质改变**——从信息工具变成代办服务，会引入责任问题
  2. **技术上做不到**——实测所有申报系统均需注册 + 手机验证，免登录拿不到
  3. 一旦声称能做，面试必被问"你凭什么保证准确性、出错谁负责"，**答不好比不做更糟**
- **代价是什么**：功能少一块，"能帮用户办成事"的叙事弱一点。换来的是边界清晰、责任可控。
- **对应面试问题**：「AI 系统给出错误建议导致用户损失，你怎么处理？」  
  → 答：① 系统定位是"信息工具"不是"代办服务"，这个边界写在 README 里；② 所有判定都附原文摘录，用户可自行核对；③ 信息不足时返回 UNKNOWN 主动追问，不硬答；④ 不做超出政策原文的推断。

### D07 · 弃用「政策问答」栏目（zcwd）

- **日期**：2026-09-24
- **结论**：主源只用 `szfwj` + `bgtwj` 两个，不使用 `zcwd`。
- **为什么不选另一个**：
  1. **内容不对口**——`zcwd` 是全站政策问答（高考科目、港澳台入学、失业保险金、买房、特困供养），与大学生政策基本无关
  2. **新鲜度差一档**——最新到 2025-11，而 `szfwj` 到 2026-09、`bgtwj` 全部是 2026
  3. **结构还多一套**——它是标准 HTML `<a>` 标签，和另两个源的 inline JS 结构不同，多维护一套解析不划算
- **代价是什么**：少了一个"口语化问法"的参考源（原计划想用它构造评测集的口语化问题）。替代方案：评测集的问题直接向真实学长学姐收集，比从问答栏目抄更真实。
- **对应面试问题**：「你怎么判断一个数据源该不该用？」  
  → 答：**先看它有没有我要的内容，再看它新不新，最后才看它好不好爬。** 三个顺序不能反——`zcwd` 就是"好爬但内容不对"的典型，如果按"好爬优先"的顺序，会浪费时间去解析一个没用的源。

### D08 · 分页 URL 拼错不会报错，必须做条数断言

- **日期**：2026-09-24
- **结论**：分页抓取必须对**每一页**做条数断言，不能只检查总数。
- **为什么不选另一个**：实测 `szfwj` 的分页规律是 `index_{N-1}.shtml`。而拼错的地址 `index1.shtml`（**少一个下划线**）**返回 HTTP 200、188898 字符的正常页面，但抽到 0 条政策**。程序不报错，只是静默少抓数据。
- **代价是什么**：每页多一次断言判断，代码略长。换来的是"错误在发生的地方暴露"。
- **对应面试问题**：「爬虫抓少了数据你怎么发现？」  
  → 答：① 每页断言条数（0 条或低于阈值直接报错）；② 记录每页的首尾标题，人工抽查排序是否连续；③ 总数和分页数做交叉验证（页数 × 每页条数 ≈ 总数）。

### D09 · 原始 HTML 必须落盘，解析逻辑可回归重跑

- **日期**：2026-09-24
- **结论**：每次抓取都把原始 HTML 存到 `data/raw/{源}_page{N}.html`，解析产物另存 `data/processed/list.jsonl`。
- **为什么不选另一个**：只存解析结果的话，解析逻辑一旦改错（比如正则漏了某种格式），必须重新爬一遍才能验证。而重爬既慢，又给对方服务器增加不必要的压力。
- **代价是什么**：磁盘占用（实测 6 页 = 700KB，可接受）。`data/raw/` 已加进 `.gitignore`，不入库。
- **对应面试问题**：「爬虫遇到页面改版怎么办？」  
  → 答：① **抓取数量做断言**（0 条或低于阈值直接报错，不静默通过）；② **保存原始 HTML 到 `data/raw/`**，改版后可用历史数据回归测试解析逻辑，不用重爬；③ 每页记录首尾标题，人工抽查排序是否连续。

### D10 · 编码问题要用代码验证，不靠肉眼看终端

- **日期**：2026-09-24
- **结论**：验证"数据文件是否正常"必须写脚本检查（BOM / UTF-8 解码 / 逐行 JSON 解析 / 乱码特征字符 / **与真实来源对比**），不能靠 `Get-Content` 之类终端输出判断。
- **为什么不选另一个**：实测 PowerShell `Get-Content` 显示 JSONL 中文为乱码，但 Python 读回来完全正常——**是终端编码问题，不是数据问题**。如果靠肉眼判断，会把"显示问题"误当成"数据损坏"，然后去改本来没问题的写入逻辑。
- **代价是什么**：多写一个 `verify_data.py`。换来的是每次都能确定"数据是对的"，而不是"看起来是对的"。
- **对应面试问题**：「你怎么保证爬下来的数据是对的？」  
  → 答：五层检查——① 无 BOM；② UTF-8 可解码；③ 逐行 JSON 可解析；④ 无乱码特征字符；⑤ **与真实来源抽样对比**。前四层只验证格式没坏，第五层验证内容对了。

### D11 · 单次代码量 ≤200 行，首次已被违反（记为教训）

- **日期**：2026-09-24
- **结论**：维持 ≤200 行限制。`crawl.py` 写了 270 行，**首次违反**，记录在案，不回头改（改它比留着更费事），但后续必须遵守。
- **为什么不选另一个**：不是"想少写代码"，是因为**所有者的能力短板是读代码**。读代码有带宽上限：**200 行能逐行看懂，270 行就会变成"看过但没懂"**。每个模块超一点，20 周后就是几千行看不懂的存量——**正是原计划列为最高风险的那个失败模式**（AI 生成代码越堆越多，最后解释不了）。
- **违反的原因（值得记）**：把"一个模块"当成了"一个文件"。`crawl.py` 其实是**两件事**：抓取逻辑 + 防错检查，拆开每个都在 200 行内。**是拆分没做好，不是内容太多。**
- **代价是什么**：模块数量变多，文件更碎，调用关系多一层。换来的是每个模块都能被完整消化。
- **对应面试问题**：「你怎么管理 AI 生成的代码？」
  → 答：**我给自己定了单次代码量上限，因为目标是"能解释每一行"而不是"尽快跑通"。这条规则第一次就被违反了，我记录下来并调整了拆分方式。** 这比说"我用 AI 提效"有说服力——它证明你在**管理** AI，而不是被 AI 推着走。

### D13 · 不用 Scrapling，继续用 requests + BeautifulSoup

- **日期**：2026-09-25
- **结论**：不引入 Scrapling（隐身爬虫库）。抓取继续用 `requests` + `BeautifulSoup` + 正则。
- **为什么不选另一个**：
  1. **要抓的站不需要反爬绕过**——实测武汉市政府、房管局均免登录、无验证码、6 轮并行抓取未触发限制，`robots.txt` 不存在。**我们的困难是"不知道抓哪个站"，不是"被封锁"。**
  2. **和核心目标冲突**——Scrapling 引入 playwright / patchright / browserforge / curl_cffi 等数十个依赖（playwright 还要下载几百 MB 浏览器内核）。**所有者的核心目标是"读懂每一行代码"，引入黑盒等于放弃控制权**：出问题时无法判断是"网站改了"还是"隐身逻辑出岔"。
- **代价是什么**：如果目标站将来开始要验证码 / 封 IP / 内容改成必须执行 JS 才渲染，需要回头引入。**这个代价可接受**——因为那时会有明确的触发条件，而不是现在凭空预防。
- **什么条件下重新评估**：① 出现验证码；② IP 被封；③ 内容必须执行 JS 才渲染。
- **附带收获**：查 Scrapling 依赖时发现它有个 `rag` 依赖组，含 `markdownify`——**"HTML 转干净 markdown"正是我们后续清洗正文要做的事，这个小组件（而非整个 Scrapling）可能有用**，待评估。
- **对应面试问题**：「你怎么选第三方库？」
  → 答：**先看它解决什么问题，再看我有没有那个问题。** Scrapling 解决"被反爬封锁"，而我们实测的目标站不封锁——**装它是解决一个不存在的问题，还引入了几十个我看不懂的依赖。** 我把它记进决策记录，并写明了"什么条件下会重新评估"，而不是简单说"不用"。

### D14 · 两类政策源互补，加 `source_role` 字段区分

- **日期**：2026-09-26
- **结论**：政策数据源分两类，**都要用**，用 `source_role` 字段区分：
  - `"discovery"` —— 用于**发现**新政策（要新、要全，如 `bgtwj` 深翻页）
  - `"content"` —— 用于**获取原文**（格式完整，如 `jzwh` 的政策清单解读版）
- **为什么不选另一个**：实测两类文件互补——
  **原始红头文件**（78号文）有条款但**没有"申报对象/申请材料/受理部门"**（5,820 字）；
  **政策清单解读版**（jzwh 那篇）七段式完整（13,472 字）但属二手。
  **只取一类都会缺东西**：只取原始文件，判定层能算条件但给不出"去哪办"；
  只取解读版，拿不到权威条款原文。
- **代价是什么**：数据模型多一个字段，抓取要维护两套解析。语料量翻倍。
- **对应面试问题**：「你的数据源怎么选的？」
  → 答：**我一开始以为"旧栏目"就该弃用，后来发现栏目停更 ≠ 政策失效**。
  那个栏目里的政策清单解读版，七段式完整，是**获取申报流程信息的最佳来源**；
  而市政府文件栏目里的原始红头文件，**有条款但没申报信息**。
  **两类文件的信息是互补的，所以我都抓，用 `source_role` 字段区分用途。**

### D15 · 硬指标失败时，必须先查"失败原因"

- **日期**：2026-09-26
- **结论**：**"硬指标 0 命中"不等于"源不对"。** 失败时必须先区分两种原因，再下结论。
- **为什么不选另一个**：实测踩过——我爬了 `bgtwj` 前 3 页（90 条），
  用两个关键文号做硬指标，0 命中，**直接判定"源不对，要换"**。
  而 `武政办〔2022〕78号` **就在第 10 页**。**差点误杀一个合格的源。**
- **代价是什么**：每次硬指标失败，多一步"翻页范围检查"。
  换来的是不误判——**误判的代价是换掉正确的源，然后重新找一圈。**
- **已落到代码**：`scripts/checks/data_checks.py` 的 `check_source_usefulness`
  在硬指标失败时**报 warn 不报 fail**，并附翻页提示；
  抓到页数 ≤5 时主动提醒"先确认翻页范围"。
- **对应面试问题**：「你的爬虫怎么判断抓够了？」
  → 答：**用布尔判断（能不能搜到目标文号）比用比例判断（关键词命中率）硬，
  但布尔判断有个陷阱——它告诉你"不在"，不告诉你"为什么不在"。**
  "源不对"和"翻页不够"的应对**完全相反**（换源 vs 继续翻），
  我只做了布尔判断就下了结论，结果差点把合格的源换掉。
  **这让我加了一条检查：硬指标失败时报 warn 不报 error，并强制提示"先查翻页范围"。**
