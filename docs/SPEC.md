## 1. 产品定义

### 1.1 一句话

输入个人画像，输出「**能享受哪些武汉大学生政策 + 省多少钱 + 依据哪一条 + 还缺什么**」。

### 1.2 为什么不是问答

这是本项目的立项理由，面试必讲：

| | 政策问答 | 政策判定 |
|---|---|---|
| 市场状态 | 红海（"十份简历八份带 RAG"） | **GitHub 搜 `补贴 资格 大模型` = 0 结果** |
| 对错 | 主观，难评测 | **确定，可自动评测** |
| 检索的角色 | 就是产品本身 | 只是前置步骤 |

调研报告 §9.2 实测：15 个相关政策类公开仓库，**没有一个给出准确率数字**。§12.4 指出三件别人都没做的事——**判定闭环 / 真实评测集 / 冲突处理**。这三件就是本项目要做的。

### 1.3 用户故事

- 作为 2026 届毕业生，我想知道能不能申请人才租赁房，系统告诉我**卡在哪一条**，而不是笼统说"不符合"。
- 作为 2022 年前就在武汉工作的申请人，系统告诉我适用**老政策还是新政策**（而不是默认取最新）。
- 作为信息不全的用户，系统**主动问我还缺什么**，而不是硬给一个答案。

### 1.4 非目标（明确不做）

- ❌ 不做通用政策问答 / 闲聊
- ❌ 不做全国、全省——**只做武汉市**
- ❌ **不做"引导用户申请"**——见下方说明
- ❌ 不做向量检索（理由见 §3.1）
- ❌ Phase 1 不做 LLM 条件抽取（Phase 2 才做，理由见 §6）

> **为什么明确不做"引导申请"**（这是一个刻意的边界，面试可讲）：
> 1. **性质会变**——从"信息工具"变成"代办服务"，而政策申报有官方渠道，学生项目不该也不能承担这个角色
> 2. **技术上做不到**——调研实测所有申报系统均需注册 + 手机验证，免登录拿不到
> 3. **面试会减分**——一旦声称能做，面试官会问"你凭什么保证准确性、出错谁负责"，答不好比不做更糟
>
> **做的是"指路"，不是"引导"**：判定完成后附上政策原文里已有的「受理部门及联系方式」，让用户知道去哪办。
> **边界：告诉你去哪办（原文抄录），不告诉你怎么填表（需要判断）。**

### 1.5 成功标准（四条，缺一不可）

1. **能判**：输入画像，输出 `ELIGIBLE` / `INELIGIBLE` / `UNKNOWN`
2. **能算**：计算类条件输出具体金额（如"每月省 600 元"）
3. **能引**：每条判定带政策名 + 文号 + 原文摘录
4. **能问**：信息不足时返回 `UNKNOWN` 并列出缺哪些字段，不硬答

## 2. 数据契约（全 SPEC 最重要的章节）

### 2.1 政策文档 `data/processed/policies.jsonl`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `doc_id` | str | ✅ | 唯一标识（详情页 URL 末段或 uuid） |
| `url` | str | ✅ | 详情页 URL |
| `title` | str | ✅ | 政策名 |
| `doc_number` | str | ✅ | 文号，如 `武政办〔2022〕78号`；缺失填 `""` |
| `publish_date` | str | ⬜ | `YYYY-MM-DD`；**缺失填 `""`**（报告：约 1/4 页面无可靠日期） |
| `region` | str | ✅ | `市级` / `江岸` / `江汉` / … |
| `template_family` | str | ✅ | `A`~`G`，模板族（见 §3.3） |
| `content` | str | ✅ | 正文纯文本（已清洗） |
| `crawled_at` | str | ✅ | ISO 8601 |
| **`policy_status`** | str | ✅ | **`现行` / `已废止` / `部分失效` / `未核实`**（见下） |
| **`status_verified_at`** | str | ✅ | 最后一次核实有效性的日期（ISO 8601） |
| **`status_evidence`** | str | ⬜ | 核实依据，如"2026-08-28 市人社局提案答复仍在引用" |
| **`superseded_by`** | str \| None | ⬜ | 被哪份文件替代（doc_number 或 url） |
| **`source_role`** | str | ✅ | **`discovery` / `content`**（见下） |

#### `source_role`：两类源是互补的，不是二选一

**2026-09-26 实测修正**（原判断"弃用停更栏目"是错的，见 `notes/decisions.md` D04/D14）。

| `source_role` | 含义 | 典型来源 | 特点 |
|---|---|---|---|
| **`discovery`** | 用于**发现**新政策 | `bgtwj` / `szfwj` 深翻页、区级目录 | 新、全，但要筛选 |
| **`content`** | 用于**获取**政策原文 | 政策清单解读版（如 `jzwh`） | 七段式完整，但属二手解读 |

**实测证据（为什么必须两类都要）**：

| | 原始红头文件（78号文） | 政策清单解读版（jzwh 那篇） |
|---|---|---|
| 正文字数 | 5,820 | **13,472** |
| 政策条款 / 条件 / 金额 | ✅ 有 | ✅ 有 |
| **申报对象 / 申请材料 / 受理部门** | ❌ **没有** | ✅ 有 |

**→ 只取原始文件**：判定层能算条件，**但给不出"去哪办"**。
**→ 只取解读版**：拿不到权威条款原文，**判定依据不可靠**。

**关键区分**：**栏目停更 ≠ 政策失效。**
`jzwh` 专题页最后新增内容停在 2023（是事实），
但它里面那篇解读**正文 13,472 字、七段式完整**，**作为"取原文"的源格式最好**。
2026 年官方仍在反复引用其中的 78 号文条款。

> ⚠️ `publish_date` 允许为空是**刻意的**——报告实测多个区级页面无日期。**不要为了填满字段而编造日期。**

#### 为什么必须有 `policy_status`（四个字段的由来）

**所有者的两次追问引出了这个缺口：**
> "武政办〔2022〕78号是 2022 年的，现在 26 年了，查这个对吗？"
> "如果找到的都是旧政策，不是误人子弟？"

**关键区分**：**「最新政策」和「现行有效政策」是两回事。本项目要的是后者。**

政策文件与新闻的逻辑相反——**规范性文件默认长期有效**，直到被明令废止或被新文件替代。
所以判断依据不是"2022 vs 2026"，而是"**有没有作废证据**"。

实测 `武政办〔2022〕78号`（2022-06 印发）在 2026 年仍是现行规则，四条铁证：

| 日期 | 官方动作 |
|---|---|
| 2026-09-07 | 媒体报道仍按其条款描述人才租赁房优惠（博士免 2 年 / 硕士 1 年 / 7 折） |
| 2026-08-28 | 市人社局提案答复称「我市**现行**人才安居政策」 |
| 2026-08-25 | 洪山区住更局按该文件答复群众 |
| 2026-07-13 | 市住房和城市更新局按该文件答复群众 |

**没有这四个字段会发生什么**（推演）：

> 2027 年面试官装一个毕业生，系统答「你可享受 X 优惠，依据 武政办〔2022〕78号」。
> 但那份文件在 2027 年 3 月已被替代。
> **系统全套自检都是绿的**——格式正确、原文摘录准确、引用无误——**只有答案是错的。**

**这正是项目自己的红线**：「程序不报错，结果是垃圾」。

#### `未核实` 这个值是必须的

理由与 §2.2 的 `ambiguity` 字段完全同构：**宁可显式承认不知道，不要默认成立。**
缺核查就填 `未核实`，判定层按 §3.5 的规则处理（带显式警告，不静默给 ELIGIBLE）。

#### 为什么必须是四个字段而不是一个

| 字段 | 缺了会怎样 |
|---|---|
| `policy_status` | 无法表达"这条还作不作数" |
| `status_verified_at` | `crawled_at` 只记录抓取时间，**不代表有效性核实过**。没有它就无法判断"这个核实结论是什么时候得出的"——而政策会变 |
| `status_evidence` | 核实结论无法被追溯、被别人反驳（与 D10「第五步对比要是真对比」同款思路） |
| `superseded_by` | 知道废止但不知道去哪找替代版本 |

> **必须在 Phase 1 数据契约定稿前处理**——否则人工标注那 150 条条件时，
> "这条现在还适用吗"这个判断无处安放，只能记在心里，150 条之后必然散掉，集体返工。

### 2.2 条件 `eval/golden_conditions.jsonl`

**这是全项目最核心的数据结构**，Phase 1 由人工标注产生。

| 字段 | 类型 | 说明 |
|---|---|---|
| `cond_id` | str | `"{doc_id}_{seq:02d}"` |
| `doc_id` | str | 所属政策 |
| **`applies_to_cohort`** | str | **适用人群分界**（见 §3.2，本项目最有技术含量的字段） |
| `cond_type` | str | `资格` \| `计算` \| `材料` \| `时序互斥` |
| `field` | str | 判定字段名，如 `education` / `grad_years` |
| `op` | str | `>=` `<=` `==` `in` `exists` |
| `value` | any | 阈值 |
| `formula` | str \| null | 计算类公式（见 §3.4） |
| `source_text` | str | **原文摘录**——用于溯源，必填 |
| `ambiguity` | str \| null | 模糊表述原文（如"积极求职创业"）；**非 null 时判定必须返回 UNKNOWN** |
| **`exempt_when`** | dict \| null | **豁免条件**。格式：`{"field": str, "op": str, "value": any}`。<br>子条件成立时本条跳过，**视为满足（PASS）**。<br>**与 `ambiguity` 互斥**——有 `exempt_when` 时 `ambiguity` 必须为 null。<br>追溯证据用 `source_text`，**不用 `ambiguity`**。 |
| **`ask`** | str \| null | **追问话术**（`ambiguity` 非 null 时给用户看的具体问题，标注时人工填） |

> **`exempt_when` 为什么必须存在**（2026-10-13 实测暴露，SPEC 原契约缺这个字段）：
> 78 号文原文「年龄不满45周岁（**研究生不受年龄限制**）」——
> `age < 45` 这一条**对研究生不适用**，但原契约里没有任何字段能表达"某个子条件成立时本条豁免"。
>
> **为什么不能用 `ambiguity` 代替**：`ambiguity` 的语义是"判不了"→ `UNKNOWN`，
> 而豁免的语义是"这条对他成立"→ `PASS`。**两者结果完全相反。**
> 没有 `exempt_when` 时，50 岁的博士会被判 `FAIL`（实测过）。
>
> **为什么不能用 `applies_to_cohort` 代替**：cohort 表达的是 grandfathering **时间轨道**
> （老政策/新政策），豁免表达的是**学历分层**。混用会让 cohort 退化成万能字段。
>
> **为什么必须与 `ambiguity` 互斥**：两者语义重叠且处置相反。
> 同时存在 = 冗余 = **改一个忘改另一个 = 静默失效**（实测来源：`_01` 原来的
> `ambiguity` 就是"研究生不受年龄限制"，加了 `exempt_when` 后两者表达同一件事）。
> 构造函数里做**断言**（不是警告）——宁可加载时就炸。

### 2.4 判定结果 `ask()` 返回值

```python
{
    "policy_id": str,
    "policy_title": str,
    "doc_number": str,
    "verdict": "ELIGIBLE" | "INELIGIBLE" | "UNKNOWN",
    "reasons": [                      # 逐条条件的结果
        {"cond_id": str, "status": "PASS"|"FAIL"|"UNKNOWN", "source_text": str}
    ],
    "missing_fields": [str],          # verdict=UNKNOWN 时，缺哪些画像字段
    "amount": {"type": "monthly"|"onetime", "value": float, "detail": str} | None,

    # ↓ 政策有效性（§2.1 的 policy_status）。判定层必须处理，见 §3.6
    "policy_status": str,             # 现行 / 已废止 / 部分失效 / 未核实
    "status_warning": str | None,     # 非"现行"时给用户的显式警告，如
                                      # "该政策状态未核实，请以官方口径为准"
    # ↓ 指路信息：从政策原文「受理部门及联系方式」段抄录，不做任何加工判断
    "where_to_apply": {
        "office": str,                # 如"租房意向区政务服务中心大学生服务窗口"
        "phone": str,                 # 可能为空
        "source_date":str,            # 该联系方式抄录自哪年的文件 ← 机构改革会改窗口
        "source_text": str            # 原文摘录
    } | None
}
```

> **`where_to_apply` 为什么需要 `source_date`**：
> 受理部门会过期——机构改革后窗口合并、电话变更都是常态。
> 抄录不带时间戳，用户会把它当成"当前有效"，**反而制造了「看起来官方其实过时」的错误信息**。
> 输出时文案要标注"来源为 XXXX 年发文，窗口可能已调整"。
>
> **另外**：`office` 和 `phone` **同时为空时返回 `None`**，不要返回空壳对象。

#### 源的分类与分工

| `source_role` | 用途 | 本文档涉及的源 |
|---|---|---|
| **`discovery`** | 发现新政策 | `bgtwj`（办公厅文件，深翻页）/ `szfwj`（市政府文件）/ 区级保障房目录 |
| **`content`** | 获取政策原文（七段式完整） | `jzwh` 专题的政策清单解读版 |



> ⚠️ **本节经过一次重大修正。** 调研报告给的首选源「就」在武汉专题页（`jzwh`）实测**已停更在 2023 年**（时间戳分布：2023 年 28 条 / 2022 年 1 条 / 2021 年 1 条），属死数据，**不可作为主源**。
>
> 原报告未验证"该源是否还在更新"——这是调研的一个盲区。**实测发现为时未晚，但已写入教训：任何数据源在正式爬取前，必须先验证时间戳分布。**

#### 主源 · 市政府政策文件（活源，2026-09-24 实测）

```
市政府文件      https://www.wuhan.gov.cn/zwgk/xxgk/zfwj/szfwj/
办公厅文件      https://www.wuhan.gov.cn/zwgk/xxgk/zfwj/bgtwj/
分页            {栏目}/index_{N-1}.shtml     第1页 = {栏目}/   每页 15 条
```

| 源 | 抽到 | 时间戳年份分布 | 判断 |
|---|---|---|---|
| `szfwj` | 15 条/页 | 2026:6, 2025:9（第1页） | ✅ |
| `bgtwj` | 15 条/页 | **2026:15（全部）** | ✅ 最新 |

**分页实测结论**：`index_{N-1}.shtml`，每页 15 条，页间**不重复**（交集检查 0 条）。

> ⚠️ **分页拼错不报错的坑**：`index1.shtml`（**少一个下划线**）返回 **HTTP 200、188898 字符**，但抽到 **0 条**。
> 程序不报错，静默少抓数据。**必须对每一页做条数断言。**

#### ❌ 已弃用：政策问答 `zcwd`

实测它虽是标准 HTML `<a>` 结构（好爬），但**内容不对口**——是全站问答（高考科目、港澳台入学、失业保险金、买房、特困供养），且最新只到 2025-11。
**教训：选源顺序是「内容 → 新鲜度 → 好不好爬」，不能反。**（见 `notes/decisions.md` D07）

#### ⚠️ 列表页解析的坑：数据在 inline JS 里，不在 `<a>` 标签

实测：`szfwj` 列表页 246 个 `<a>` 标签，**只有 3 个含 `.shtml`**（且都是页面框架链接）。
真正的政策列表藏在每条记录的 inline `<script>` 里：

```html
<li>
  <script>
    var url = "";
    if (url == ""||!url.startsWith("http")) {
        url = "./202609/t20260917_2849324.shtml"
    }
    var title = "";
    if(title==""){
        title = "市人民政府关于印发……的通知";
    }
```

**后果**：用 BeautifulSoup 的 `find_all("a")` 会**一条政策都抓不到**，且不报错——只会得到空列表。
**解析方式**：必须用正则提取 `var url = "./YYYYMM/tYYYYMMDD_ID.shtml"` 和紧随其后的 `title = "..."`。

## 3. 核心设计决策（面试要讲的，每条都要能说出「为什么」）

### 3.1 为什么不用向量检索

**结论**：Phase 1 用 `BM25 + 元数据过滤`，不建向量库。

**理由**（三条，按强度排序）：
1. **规模不够**——全部语料 80-150 条，安居类 MVP 只有 30-40 条。这个量级向量检索收益趋近于零。
2. **文号类查询必须精确匹配**——"武政办〔2022〕78号规定了什么"，BM25 远优于向量。
3. **可解释性**——判定要输出"依据哪一条"，必须定位到具体条款，元数据过滤比语义相似更可控。

**必答题预案**：「2026 年模型都 1M 上下文了，为什么还要 RAG，全塞进去不行吗？」

> 答：**我用检索不是为了解决"塞不下"，是为了"要结构化"。** 全塞进去也行，但我还是得对每条政策抽条件——那样抽取成本和错误率都更高，而且"抽漏了哪条"不可控。检索的作用是先把候选缩到 20 条，再对候选做结构化抽取。
>
> 另外两个硬理由：① **时效**——废止政策必须物理过滤，全塞会污染判定；② **多用户**——每个画像不同，不能为每个人重建 context。

**调研报告佐证**：arXiv 2603.24580 实测——"**更强的检索在语料缺失时反而导致更自信的幻觉**"（stronger retrieval counterintuitively leads to more confident hallucinations）。所以本项目不追求检索指标，追求**判定正确率**。

### 3.2 `applies_to_cohort` —— 本项目最有技术含量的一个字段

**调研报告 §7.1 实测的 grandfathering 双轨**（不是 bug，是合法的"老人老办法"）：

| 通道 | 适用人群 | 条件 |
|---|---|---|
| **老政策**（武房规〔2018〕2号） | 2022-06-07 **前**留汉、未申请人才安居资格 | 毕业 **3 年内** + 武汉户籍 + 家庭无房；70%/80% |
| **新政策**（武政办〔2022〕78号） | 2022-06-07 **起**在汉就业创业并缴社保 | 毕业 **6 年内** + 社保 + 家庭无房；70%，博士免 2 年、硕士免 1 年 |

**架构后果**：**"取最新版本"是错的。** 每条条件必须带 `applies_to_cohort`，判定时先按画像确定用户属于哪个 cohort，再取对应那一套规则。

> **这是通用 RAG 教程里绝对没有的东西。** 调研报告 §7 共发现 9 组市区冲突 + 1 组合法双轨 + 1 组校际差异，全部是官方原文对官方原文。

### 3.3 模板族（不要按"区"建解析器）

调研报告 §3.2 逐页核对 33 个区级页面后确认：**至少 6-7 个模板族，七段式覆盖率不到一半。**

| 族 | 结构特征 | 出现处 |
|---|---|---|
| **A**（主导） | 政策内容/申报对象及条件/补贴标准/文件依据/申请材料/业务流程/受理部门 | 洪山、武昌、东西湖、新洲、市级 |
| **B** | 九段式，**支持标准排在申报条件之前**（会被误抽） | 硚口 |
| **C** | 政务服务事项式，**没有"补贴标准"字段** | 汉阳 |
| **D** | 事项清单式，补贴标准降级为子段，"特别提醒"藏硬要求 | 东湖高新 |
| **E** | 五段短指南，顺序完全不同 | 江岸 |
| **F** | tab 式 | 蔡甸、新洲 |
| **G** | **非结构化**——房源通告里夹 20 个楼盘价格表 | 经开、江汉 |

> ⚠️ **族 G 是检索污染源**：直接全文切片会把 2000+ 个租金数字喂进语料。**必须单独处理或排除。**

**结论：解析器按「模板族」建，不按「区」建。**

### 3.4 计算类条件（技术深度的来源）

调研报告 §6 实测：**计算类约占 25%，形态丰富**（v1 担心的"全是纯资格类"不成立）。

最复杂的一条——人才租赁房，**六重叠加**（武政办〔2022〕78号原文）：

> 按照**不高于市场租金的70%**缴纳租金，**累计减免期限不超过3年**。其中，全日制博士、硕士**分别免缴2年、1年**租金，**免租金额每月分别不超过2000元、1500元**。3年期满后确有需要的，经本人申请**最多可再延长2年**，延长期内租金标准**按照市场价执行**。

**一条里含：比例(70%) / 时长封顶(3年) / 分层时长(博士2年·硕士1年) / 分层金额封顶(2000·1500) / 续期(+2年) / 续期后规则变更。**

其他形态：
- 公式型：`1768元/人（即武汉市最低工资标准的80%）`——⚠️ **基准值已变**，见 §7 风险
- 取小值：`两项险种合计673.19元/月/人。月实际缴费低于以上标准的，按实际缴费补贴`
- 定额+封顶：`每吸纳1名…给予1000元，补贴总额不超过2万元`

**区级加码条款**（市级完全没有，不做跨级合并就会漏）：硚口"3年免租、每月≤3000元"、经开"博士100%/100%/70%、硕士100%/80%/60%、本科80%/60%/40%"、汉阳、青山、东西湖各有不同。

### 3.5 UNKNOWN 分支与主动追问

调研报告 §5.2：**约 30% 的条件含模糊/需裁量表述**。

原文例子：`积极求职创业`、`正常经营状态`、`正常缴纳社会保险`、`零就业家庭…但不建议按此类申请`。

**设计决策**：**遇到 `ambiguity` 非 null 的条件，判定返回 `UNKNOWN` 并触发主动追问，而不是硬给答案。**

**这是能讲的设计决策**——对上面试题"**检索结果没有证据，系统应该回答还是拒答？**"（掘金 10 个追问的第 9 问）。

### 3.5b 政策有效性分支（与 §3.5 同构的第二处应用）

**这是"政策本身可能过期"的处理，和 §3.5"条款模糊"是同一个原则的两处应用。**

```
policy_status == "已废止"    → 该政策不参与判定，直接跳过
policy_status == "部分失效"  → 参与判定，但结果必须带 status_warning
policy_status == "未核实"    → 参与判定，但结果必须带 status_warning（不静默给 ELIGIBLE）
policy_status == "现行"      → 正常判定
```

**为什么不把"未核实"当成"现行"**：那等于默认成立。
**为什么不把"未核实"当成"已废止"**：那会漏掉真实可享受的政策。
**正确做法**：照常判定，但**显式告诉用户"这条我还没核实是否仍然有效"**。

**为什么"已废止"要跳过而不是带警告**：给一个已废止的政策做资格判定，
无论结果是什么都是错的——**ELIGIBLE 是错的（申请不了），INELIGIBLE 也是错的（误导用户以为只是自己不符合）**。

> **面试价值**：这套输出同时回答了「我能不能享受」和「这条还作不作数」两个问题。
> **后者是市面上所有政策问答产品都没做的事**（调研报告 §12.4 论证过的空白）。

### 3.5c 条件判定的九格输入真值表（2026-10-19 所有者批，落点经 wb 建议）

> **来源**：F2 事故（wb 2026-10-13 指出）。豁免字段的测试覆盖了 9 种输入形态里的 8 种，
> 恰好漏了出事的那格（④缺豁免字段）——说明**"加断言"这个动作本身需要一份"该测哪些输入"的清单**，
> 否则测的永远是"我想到的输入"。本表就是那份清单，**判定逻辑改动时逐格对照**。

| # | 输入形态 | 正确行为 | 已有断言 |
|---|---|---|---|
| ① | 正常通过 | PASS | ✅ |
| ② | 正常不过 | FAIL | ✅ |
| ③ | 缺主字段 | UNKNOWN + 追问主字段 | ✅ |
| ④ | **缺豁免字段**（且正常 FAIL） | **UNKNOWN + 追问豁免字段**（F2：不许判 FAIL） | ✅ 修复时补 |
| ⑤ | 豁免命中（且正常不过） | PASS + 标 `exempted` | ✅ |
| ⑥ | 豁免不命中 | 按正常判定 | ✅ |
| ⑦ | ambiguity 模糊表述 | UNKNOWN（不许硬答），与 `exempt_when` 互斥 | ✅ |
| ⑧ | cohort 不适用 | N/A（不进 verdict） | ✅ NF-1 补 |
| ⑨ | 缺分界字段（cohort 判不了） | UNKNOWN + 追问分界字段 | ✅ NF-1 补 |

**用法**：给判定逻辑新增分支（豁免、计算、版本冲突…）时，**先问每一格在这个分支下的行为**，
答不全就是测试还没写全。故障注入（`python -m src.engine.eligibility`）应覆盖全部 9 格。

> ⚠️ **本表自身的教训（NF-1，wb 2026-10-19）**：首版 ⑧⑨ 标了 ✅ 但实际**只有实现没有断言**
> ——「行为存在」被写成了「断言已有」。九格表的 ✅ 列是它的核心功能，标错一格表就失去存在意义。
> **教训**：往这种表里标 ✅ 前，必须在测试代码里 grep 到对应断言，不能凭"引擎有这个行为"推。

### 3.6 判定用纯代码，不用 LLM

**`check_eligibility` 和 `calc_amount` 是纯 Python，不调任何模型。**

理由：**可判定的事不交给模型。** LLM 负责"从文本抽条件"（Phase 2），不负责"比大小"。

**对应面经追问**：美团"Agent 输出的 JSON 有时不对，怎么做 Schema 校验和重试"、凌脉"工具调用前如何校验参数，避免模型传入错误或危险参数"。

| 5 | **人工标注** | golden_conditions.jsonl，30-40 条政策 | — |

| 7 | `cohort.py` | 人群分层 | ~70 |

| 9 | `calc.py` | 金额计算 | ~120 |

**Phase 1 学习检查点（5 问，合格线 4/5）**

3. `eligibility.py`：`UNKNOWN` 分支和 `INELIGIBLE` 的区别是什么？为什么不能把 UNKNOWN 当成 INELIGIBLE？

5. `evaluate.py`：三类 verdict 的准确率为什么要分开算？混在一起算会掩盖什么？

### Phase 2 · LLM 条件抽取（第 11-13 周）

- 失败重试 + 抽不出的降级到人工

### Phase 3 · 冲突处理与差异化（第 14-18 周）

- grandfathering 双轨完整落地
- 9 组市区冲突：**冲突时显式暴露双方证据**，不静默取一个
- 校际执行差异
- README + `docs/DESIGN.md`

## 7. 已知风险

| 风险 | 概率 | 影响 | 预案 |
|---|---|---|---|
| **工期不够**（18 周 vs 需 20+ 周） | **高** | **高** | Phase 1 结束即投，不等 Phase 2/3。砍顺序：Phase 3 → Phase 2 → 减少政策条数 |
| **人工标注被低估** | **高** | **高** | 30-40 条 × 平均 5 条条件 = 150-200 条条件。**排 2.5 周，不能压缩** |
| 政策金额基准过期 | 高 | 中 | 最低工资 2025-12-01 已从 2210 调至 **2400 元**，但 2026 届补贴文件仍写 **1768 元**。**必须在数据里记录"文件写的值"和"按公式算的值"两个数**，并显式暴露差异 |
| 模板族 G 污染语料 | 中 | 中 | 单独处理或排除；不要把房源通告的价格表喂进语料 |
| 页面无发布日期 | 高 | 中 | `publish_date` 允许为空；**不允许编造** |
| 抽取准确率不达标 | 中 | 中 | 行业上限 82%，政务一线要求 >90%。**如实报告，不美化** |
| 找不到真实用户 | 中 | **高** | 目标 20 个 2026 届学长学姐。**这是简历上最难替代的一句话** |

## 8. 编码约束

1. 命名全 snake_case；常量全大写
2. 每函数中文 docstring；关键行写「为什么」
3. **禁止静默吞错**（`except: pass` 直接打回）；解析层宽松跳过但记 warning
4. 所有批量任务按 `doc_id` 幂等，支持中断续跑
5. 所有批量任务打印 `[当前/总数] 进度 + 预计剩余时间`
6. 所有文件读写显式 `encoding="utf-8"`
7. 类型注解：公开函数必须带
8. **禁止引入 `requirements.txt` 之外的依赖**
9. git 提交：`feat(模块): 描述`，每模块小步提交
